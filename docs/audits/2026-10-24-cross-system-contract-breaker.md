# Cross-System Contract Breaker Audit

**Product:** KYX / Pulse Forge  
**Date:** 2026-10-24  
**Scope:** Parameter intent and effect state through command execution, MCP acknowledgement, automation, persistence, undo, and offline audio.  
**Evidence rule:** PASS means the named path was exercised by a test or runtime probe. Source inspection alone is marked PARTIAL or UNKNOWN where runtime behavior matters.

## Executive summary

The project has unusually strong command, automation, persistence, and MCP guards. The project document is the state authority; effect writes use the shared parameter definitions; live and offline scheduling converge on the same `AudioEngine` entry points; and the selected regression suites passed.

One confirmed contract break was found and fixed: a relative parameter ask targeting a family of tracks was previewed from each track's own value but applied using only the first track's value. A regression now drives the plan and command through a real `ProjectStore`, verifies the values agree, and verifies one undo restores the document.

The current working tree also contains an unrelated, unfinished `AudioEngine.ts` change and an untracked mixer-strip test from another session. The committed source at audit start used smoothed `AudioParam` writes while initializing offline graph controls. That path deserves PCM verification; the in-flight edit is not treated here as an audited fix. The real-browser probe measured effect-parameter changes, but it did not measure mixer-strip initialization.

No human listening check, native audio-device check, full `renderProject` PCM comparison, or real crash/recovery interruption was performed. Reliability is strong for the tested document and command boundaries, but end-to-end equivalence across every audio, persistence, and AI boundary remains unproven.

## Findings

### F-01 — Relative family plan disagreed with the applied values

- **Severity:** P2 (reproducible partial inconsistency; document change is undoable)
- **Affected subsystems:** Intent plan, parameter command compilation, MCP read-back for family targets.
- **Evidence:** CONFIRMED; reproduced in a temporary probe, then fixed and pinned by `tests/param-intent.test.ts`.
- **Reproduction:** Create two bass-role tracks with reverb decay values `1 s` and `10 s`. Ask “slightly longer reverb decay on the bass.” Before the fix, `paramPlan` previewed `1.1 s` and `11 s`, while `applyParamIntent` derived `1.1 s` from the first track and wrote `1.1 s` to both. The plan and actual project state disagreed.
- **Expected:** Each target receives the relative change from its own current value, matching the preview and subsequent read-back.
- **Root cause:** The apply path made one `MixDecision` per family and sampled only `ids[0]`; `applyMixIntent` then fanned that one value out to all family tracks. The plan and read-back enumerated tracks individually.
- **Fix:** `applyParamIntent` now makes one decision per resolved track, deduplicates overlapping targets, and uses that track's current value. The regression uses a real `ProjectStore`, checks both resulting values, verifies one history entry, and undoes to the prior document.
- **Remaining risk:** The routed `kyx_intent` result for this exact multi-track relative scenario is not yet driven end-to-end through a real MCP context.

### F-02 — Offline mixer-strip initialization needs PCM coverage

- **Severity:** P2 (potentially incorrect opening audio for non-default gain, pan, mute, send, or preset normalization)
- **Affected subsystems:** Project document → `AudioEngine.syncProject` → `OfflineAudioContext` render.
- **Evidence:** PROBABLE. The committed source at audit start scheduled initial gain/pan/send values with `setTargetAtTime(..., currentTime, 0.01)`. A newly created offline graph starts at each `AudioParam` default; scheduling a target at render time zero can leave a startup envelope from that default instead of applying the project value at the first sample. No before-fix PCM capture was run in this audit.
- **Reproduction to close:** Render isolated tracks from sample zero with gain `0.5`, mute enabled, hard pan, and a nonzero send; compare the first 50 ms and steady-state PCM to expected values and to a render with direct initial assignment. Include controls for unity gain, center pan, and unmuted state.
- **Current tree state:** Another session has an unstaged `AudioEngine.ts` change introducing `writeStripControl` and an untracked `tests/offline-mixer-strip.test.ts`. Those files are outside this audit's changes; the proposed mitigation was not included in the focused test command or independently reviewed here. Do not treat it as a verified fix yet.

No other confirmed contract break was found in the tested sample. The gaps below are evidence gaps, not claims that those operations are defective.

## Top 5 strategic architecture recommendations

1. Keep one resolved-target list as the shared input to preview, apply, read-back, and MCP response construction; the F-01 failure was a second interpretation of the same target family.
2. Make operation results carry structured target-level outcomes and the stage that was reached. Keep `mutated` as a compatibility field, but do not make it stand in for persistence or DSP confirmation.
3. Maintain a small set of browser-backed “musical intent to PCM” fixtures that cross commands, automation, save/load, and full export. Keep unit tests for precise invariants and use browser probes for sound-path claims.
4. Document writer precedence for base values, automation lanes, modulators, scene overrides, and manual gestures, then pin the ordering at the scheduler/AudioEngine boundary.
5. Preserve independent diagnostics for command rejection, persistence failure, runtime degradation, and render output. A single success string obscures which boundary actually completed.

## Open questions and residual risks

- Does `kyx_intent`'s new target-level parameter read-back run against a real store and expose `partial`/`no_value_moved` truthfully for a family containing both matched and unmatched targets?
- Does the pending offline strip-control change cover all initial control writes, or only `syncProject` writes? Direct runtime setters still have smoothing behavior and need separate ownership/timing review.
- Should a relative family ask apply an equal physical increment to every target (the behavior pinned by the plan) or converge all targets to the first target's resulting value? This audit treats the existing per-track plan as the user-visible contract.
- Are automation and manual parameter edits defined to take effect immediately, at the next scheduler window, or after the current lane segment? This was not validated here.
- Native audio I/O, external plug-in host behavior, hardware latency, and human listening remain outside this audit's tested scope.
