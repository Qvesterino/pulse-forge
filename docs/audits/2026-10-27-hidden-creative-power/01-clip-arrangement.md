## 1. Method and limits

**Method.** Enumerated every exported command factory in the 16 in-scope `src/commands/*.ts` modules (152 exported functions across `clipEditing` 12, `audioClips` 18, `automationClips` 15, `scenes` 13, `quantize` 12, `midiClips` 11, `groove` 11, `patterns` 10, `arrangement` 10, `clipPlayback` 8, `chordTrack` 8, `arrangementShapes` 7, `markers` 5, `clipGroups` 5, `clipClipboard` 4, `timeRange` 3), then for each one searched `src/` (excluding `src/commands/`) for the function name AND for its raw command-type string, to catch dispatch-by-type. Cross-checked the three reachable dispatchers: the central shortcut table (`src/ui/shortcuts.ts:109` `SHORTCUTS`, `src/ui/shortcuts.ts:303` `EDITOR_SHORTCUTS`), the command palette (`src/ui/commandPalette.ts:54` builds actions _only_ from `getActiveShortcuts()`, plus 4 hard-coded extras at `:77` — snapshot, gallery, history, diagnostics), and the per-clip right-click menus. Read the relevant specs to establish the verified contract (not run — per instructions).

**No generic command dispatcher exists.** A command with no shortcut key, no palette entry, no menu item and no direct call site is unreachable from the GUI. This is the load-bearing fact behind findings HCP-01-01/03/04.

**Shared-worktree drift.** Other agent sessions were editing this repo concurrently while this audit ran; `src/commands/{arrangement,arrangementShapes,audioClips,automationClips,clipClipboard,clipEditing,clipPlayback,midiClips}.ts`, `src/project-model/{types,schema}.ts`, `src/ui/{App,ArrangementPanel}.tsx` all changed under me mid-audit. Every line number below was re-derived against the working tree **after** the last such change and re-validated (206 citations, 0 unresolved paths, 0 out-of-range lines, content spot-checked). If a peer commits later, expect the line numbers in this file to drift by a few lines even though the symbols do not move.

**What I could NOT verify.**

- I did not run the app, the dev server or the test suite (per instructions). Every "Runtime status" below is _code-traced_, not observed. Nothing here is `Observed in running app`.
- I did not audit the ARR-0025 drag/resize gesture internals line by line (`ArrangementPanel.tsx:2400–3400`); I traced their command targets and their tooltips, and cite the gesture surface only where a tooltip or handler names it.
- I did not verify WebAudio output correctness of any of these verbs — only that the command is wired, reachable and undoable.
- `src/mcp/tools.ts` (~12 000 lines) was sampled, not exhaustively read; where I claim "MCP-only" I searched the whole `src/` tree and found no non-MCP caller.

**Confidence legend.** `Verified in code/tests` = read the implementation and at least one spec or a second call site. `Inferred` = read the implementation, single call site, no spec. `Hypothesized` = plausible from naming only — used once, explicitly flagged.

## 3. Candidate findings

### HCP-01-01 — The whole natural-language pattern-verb engine is orphaned

**Class: H (dead code, traced).**
Evidence: `src/intent/pattern-verbs.ts:62` `parsePatternVerbs` parses EN + SK pattern-diff verbs; `src/commands/groove.ts:328` `applyPatternVerbsCommand` turns them into one undoable snapshot. Repo-wide search for both symbols returns only their own definitions plus `tests/pattern-verbs-audit.test.ts:3–128`. Neither the Intent panel, the MCP surface, nor the pattern bar calls them.
Why a user misses it: the feature is _specified_ in the module header ("fewer hats", "menej hi-hatov", "denser snare", "add ghosts", "simplify", "swing it") as if it were a user-facing capability, and the intent parser's sibling `src/intent/arrangeWords.ts` **is** wired into the context-menu Producer editor — so a user who finds one NL editing surface reasonably expects the other to work.
Minimal intervention: call `parsePatternVerbs` from the existing Intent-panel routing and map its result to `applyPatternVerbsCommand`; add one "fewer hats" button in `PatternBar.tsx` next to mutate/fill. No new model, no new command.

### HCP-01-02 — Marker editing is read-only in the GUI while the whole model is written for it

**Class: H (rename/type/move/link) + D (add/remove).**
Evidence: the command layer owns five marker verbs (`src/commands/markers.ts:23,41,47,54,60,71`), the marker type taxonomy (`src/project-model/types.ts` `Marker["type"]` = cue/drop/buildup/riser/impact/custom) and a live cue-FX consumer (`src/project-model/markers.ts:8` → `src/scheduler/Scheduler.ts:1141–1153`). The GUI can only **add** a `cue` marker (`src/ui/ArrangementPanel.tsx:5323` hardcodes `type: "cue"`) and **delete** by right-click proximity (`ArrangementPanel.tsx:5386`). `renameMarker`, `setMarkerType`, `moveMarker` and `setMarkerLinkedClip` have no GUI call site — searched all of `src/` outside `src/commands/`; the only callers are `src/collab/jamRoles.ts:49,50,194,196` and (for rename) `src/mcp/tools.ts:6142`.
Why a user misses it: a marker chip renders with `title={`${marker.name} (${marker.type})`}` (`ArrangementPanel.tsx:5402`) — the type is _visible but unchangeable_. Non-cue markers (which are the ones that fire a riser/impact cue during playback) can only be produced by AUTO ARRANGE, so the cue-FX feature is effectively invisible unless you happen to auto-arrange.
Minimal intervention: make the marker chip open a small popover (name input, type select, "link to selected clip", "delete"); route it to the four existing commands. No model change.

### HCP-01-03 — Splitting MIDI and automation clips has no entry point at all

**Class: H.**
Evidence: `src/commands/midiClips.ts:350` `splitMidiClipAtTick` and `src/commands/automationClips.ts:185` `splitAutomationClipAtTick` both exist, are exported through the barrel (`src/commands/commands.ts:51,17`), are covered by specs (`tests/tick-lane-edit-matrix.test.ts`, `tests/timeline-structural-clips.test.ts`), and are called — but **only** from inside range consolidation (`src/commands/timeRange.ts:668,669`). The MIDI lane menu (`src/ui/arrangement/MidiClipLanes.tsx:452–477`) offers Edit source pattern / Duplicate / Make unique / Mute / Delete — no Split. The automation lane menu (`src/ui/arrangement/AutomationClipLanes.tsx:666–705`) offers Duplicate / Mute / Lock / Delete — no Split. The CUT tool only exists for scene and audio clips (`ArrangementPanel.tsx:5821,5967`); the lanes never read `toolStore`.
Why a user misses it: the CUT tool's own tooltip promises timeline-wide splitting — "click any clip to split it at the click position (V = select, C = cut). Scene clips split on their bar grid, **audio clips sample-precise**" (`ArrangementPanel.tsx:5153`) — and the help overlay's "Arrangement keys" section lists Ctrl+E as "Separate the audio clip at the playhead" (`shortcuts.ts:356`). Both describe _audio_; the MIDI and automation lanes are on the same arrangement surface but silently opt out.
Minimal intervention: add "Split at playhead" to the two lane menus and make the lanes honour the CUT tool, reusing `splitMidiClipAtTick` / `splitAutomationClipAtTick`.

### HCP-01-04 — Three distinct "consolidate" operations behind two identical labels

**Class: E (inconsistent) + B (one is undiscoverable).**
Evidence: (a) `src/commands/timeRange.ts:720` `consolidateTimeRangeToAudio` renders a whole **range** to one audio print — reachable via `Ctrl+Shift+C` (`src/ui/App.tsx:1536`) and via the context-menu "Consolidate" (`src/ui/ContextMenu.tsx:653`), which opens a _text-input_ Producer dialog pre-filled with "consolidate selected range" (`ContextMenu.tsx:366`). (b) `src/commands/clipEditing.ts:612` `consolidateAudioClips` renders selected **audio clips** into a persisted asset — reachable via the audio-clip menu, also labelled "Consolidate" (`src/ui/ArrangementPanel.tsx:6978`). (c) `src/commands/timeRange.ts:388` `consolidateTimeRange` is a third, legacy musical-only variant with no GUI entry at all (`src/collab/jamRoles.ts:218` only); its own doc comment calls it "Legacy … remains for callers that explicitly want pattern material" (`timeRange.ts:384–386`).
Why a user misses it: the same word means "replace this time range with a full-mix print" in one surface and "render these clips into an asset" in another, and the keyboard shortcut for the first is absent from `SHORTCUTS` (`src/ui/shortcuts.ts:109`), `EDITOR_SHORTCUTS` (`:303`) and therefore from the command palette (`src/ui/commandPalette.ts:54`). A user reading the help overlay ("?") cannot find Ctrl+Shift+C anywhere.
Minimal intervention: rename (a) "Consolidate range to audio" and (b) "Render clips to audio asset"; add "Consolidate range (Ctrl+Shift+C)" to `EDITOR_SHORTCUTS` so it appears in the help overlay.

### HCP-01-05 — The arrangement's gesture grammar is documented only inside one hover tooltip

**Class: C.**
Evidence: the arrangement's whole clip-gesture vocabulary — top corners = fade, top middle = clip gain, Alt+edge = stretch, Alt+body = slip — is disclosed in a single `title` attribute: `"M mutes · PT: top corners fade, top middle clip gain, Alt+edge stretches, Alt+body slips"` (`src/ui/ArrangementPanel.tsx:5962`), on a clip that also carries the buffer id, lock/mute/reverse/loop/warp flags, trim and fade amounts and the stretch rate. The first-time gesture-hint mechanism (`src/ui/gestureHints.tsx:15`, three keys: multi-select, velocity-drag, step-editor) contains **no** arrangement or clip key. `EDITOR_SHORTCUTS` lists "Slip the audio clip's content (linear clips) — Alt + drag body" (`shortcuts.ts:361`) but not the fade, gain or stretch gestures.
Why a user misses it: the user has to hover one specific clip, parse a ~300-character string, and infer which corner does what; there is no first-run hint, no toolbar, no help entry for fade/gain/stretch.
Minimal intervention: split the tooltip into a short title plus a discoverable "clip gestures" affordance (a "?" chip on the selected clip, or three `EDITOR_SHORTCUTS` rows); add one gesture-hint key fired on first clip-gain drag.

### HCP-01-06 — "Strip Silence (PT)" and "PT separate clip" use a DAW acronym the app itself translates elsewhere

**Class: C.**
Evidence: the label at `src/ui/ArrangementPanel.tsx:6933` is `"Strip Silence (PT)"`; the code comment at `src/ui/App.tsx:1408` reads "Ctrl/Cmd+E — Separate at playhead (PT separate clip)". The app ships a DAW-vocabulary bridge precisely for this — `src/ui/dawProfile.ts:6` lists a "Pro Tools" profile and `DAW_ACTION_MAPPINGS` (`:14`) maps familiar terms to KYX terms — but that table is consumed **only** by the command palette (`src/ui/commandPalette.ts:44–75`) and contains eight concepts, none of them clip-editing.
Why a user misses it: "PT" is a Pro Tools shorthand that no KYX user is told to read; the same string appears in a user-visible button.
Minimal intervention: drop the parenthetical, or resolve it through the active DAW profile like the palette does.

### HCP-01-07 — "Ungroup" is always enabled and silently does nothing when the selection is not grouped

**Class: E.**
Evidence: `src/ui/ContextMenu.tsx:641` renders Ungroup with `disabled={!hasClips}` — i.e. enabled for any clip selection. `src/commands/clipGroups.ts:76` `ungroupClips` returns a no-op snapshot when the selection is not in a group (`clipGroups.ts:78–80`), and `src/store/ProjectStore.ts:357` discards no-op commands, so **no** toast, **no** error, **no** undo entry is produced. The keyboard path has the same behaviour (`src/ui/App.tsx:907`).
Why a user misses it: the user cannot tell from the menu that the selection is not a group; the command appears to do nothing and the app looks broken. The inverse is well handled — "Group" is disabled below two clips (`ContextMenu.tsx:637`) and the group membership _is_ visible (the `grouped` CSS class, `ArrangementPanel.tsx:5812,5960`).
Minimal intervention: compute group membership from `doc.arrangement.clipGroups` (the same lookup the `grouped` class already does) and disable/annotate Ungroup accordingly.

### HCP-01-08 — `bounceStemsToAudioClip` is exported, documented, and inert

**Class: H.**
Evidence: `src/commands/clipEditing.ts:321`. Its body computes `buildStemProject(doc, …)` and immediately discards it (`const stemDoc = …; void stemDoc;` at `:328–329`), then calls `addAudioClip(doc, trackIds[0], bufferId, …)`. The only repo references are the definition and the barrel re-export (`src/commands/commands.ts:61`) — no caller in `src/`, no spec.
Why a user misses it: it cannot be reached, so this is a maintenance trap rather than a user-facing gap: a future caller would get "add a clip with this buffer id", not a stem bounce, and the misleading name promises much more than the body delivers.
Minimal intervention: either implement the bounce (render the stem doc, add the resulting buffer) or delete the export and its barrel entry.

### HCP-01-09 — The skeleton preview is re-implemented in the UI instead of using the shared builder

**Class: E.**
Evidence: `src/commands/arrangementShapes.ts:129` `arrangementSkeletonPreview` is the shared builder, used by `createArrangementSkeleton` at `:331` — and the module header states the reason: "a preview that lays the song out differently from the real thing is worse than no preview" (`arrangementShapes.ts:4–7`). The UI's BUILD SKELETON preview does not call it: `src/ui/ArrangementPanel.tsx:5110–5121` re-derives the role list from a local `const roles = ["intro","build","drop","break","outro"]` and hardcodes the same lengths (`role === "drop" ? 16 : 8`).
Why a user misses it: the two lists agree today by coincidence; the preview also omits the scene names and shows only roles, so the user cannot tell _which_ scene will land where before clicking "APPLY SKELETON" (which replaces the arrangement).
Minimal intervention: call `arrangementSkeletonPreview(doc)` from the preview block and render the scene names it returns.

### HCP-01-10 — `setScenePattern` and `setSceneLoop` are unreachable from the GUI

**Class: H.**
Evidence: `src/commands/scenes.ts:130` `setScenePattern` — no GUI call site (searched all of `src/` outside `src/commands/`; callers are `src/collab/jamRoles.ts:178` and `src/reference/unsuno.ts:351`; the scene UI in `src/ui/arrangement/ScenesPanel.tsx:66–145` and `src/ui/SceneStrip.tsx` offers pack/macro/CC-override/modulator but no pattern binding). `src/commands/clipPlayback.ts:70` `setSceneLoop` — no GUI call site at all (`src/collab/jamRoles.ts:181` only); the LOOP button at `ArrangementPanel.tsx:5281` drives the _clip_-level `setArrangementClipLoop` (`clipPlayback.ts:75`), a different field on a different entity.
Why a user misses it: a scene's source pattern is fixed at creation time, and scene-level loop cannot be set at all — two real arrangement verbs that the model supports and the GUI omits.
Minimal intervention: add a pattern select to the scene strip (backed by the existing `setScenePattern`) and a scene-level loop toggle next to the clip LOOP button (backed by `setSceneLoop`), or mark both deprecated in the barrel if they are genuinely retired.

### HCP-01-11 — The marker→cue-asset mapping is implemented twice

**Class: E.**
Evidence: `src/project-model/markers.ts:8` `markerAssetFor` (drop→impact, buildup/riser→riser) and `src/scheduler/Scheduler.ts:1468` `mapMarkerTypeToAsset` (identical switch, plus impact→impact) are two copies of the same rule. The scheduler uses its private copy; the scorepack export (`src/export/scorepack.ts:161,282`) and the reference mapper (`src/reference/structure.ts:134`) use the shared one.
Why a user misses it: today they agree, so the divergence is invisible; the moment a new marker type is added to one table, the GUI will play a cue that the scorepack export does not contain (or vice versa).
Minimal intervention: delete the scheduler's private copy and import `markerAssetFor` from `src/project-model/markers.ts`.

### HCP-01-12 — `setMidiClipLocked` is a dead parallel of the working generic lock command

**Class: H (low impact).**
Evidence: `src/commands/midiClips.ts:428` `setMidiClipLocked` has no call site outside `src/commands/` (repo-wide search returns only the definition and `tests/midi-arrangement-clips.test.ts:13,255,326`, `tests/tick-lane-edit-matrix.test.ts:12,156`). The working path is `src/commands/clipGroups.ts:88` `setClipsLocked`, which already covers MIDI clips (`:99`, `:113`) and is what the UI uses (`src/ui/ContextMenu.tsx:313`, `src/ui/App.tsx:928`). The automation lane menu's "Lock/Unlock" (`src/ui/arrangement/AutomationClipLanes.tsx:690`) uses the automation-specific command `setAutomationClipLocked` (`src/commands/automationClips.ts:324`) instead.
Why a user misses it: it is a maintenance inconsistency rather than a user gap — three lock commands for one concept.
Minimal intervention: delete `setMidiClipLocked`, or route the automation lane menu through `setClipsLocked` so one verb owns all four clip kinds.

## 4. Verified as genuinely working (do not re-litigate)

- **Clip clipboard.** `src/commands/clipClipboard.ts:81–133` deep-clones the payload (so later edits cannot rewrite clipboard history), refuses cross-project paste (`:152`) and a paste whose source scene/pattern/target has been deleted (`:162–182`), and commits as one undoable delta (`:297`). The cut toast carries an explicit consequence line — "Copied to clipboard — Ctrl+V pastes at the playhead" (`:132`).
- **Clip grouping and lock.** `src/commands/clipGroups.ts` implements one-group-per-clip membership, drops a group that falls to one member (`:55`), and enforces `locked` at the command layer for every destructive verb (`:132–137`) — the documented choke point shared by UI, MCP and intent. Membership is visible in the UI on all four clip kinds.
- **Crossfade.** `src/ui/rangeCrossfade.ts:46` brackets the whole gesture in one undo frame so one `X` press is one Ctrl+Z step (`:52`, contract documented `:14–26`), crossfades overlapping pairs with equal-power fades first, then seam-fades the rest, and adds a `custom` transition between adjacent scene clips.
- **Ripple edit.** `src/commands/clipPlayback.ts:160/207/242` plus the ghost preview at `src/ui/ArrangementPanel.tsx:5874`; the ripple toggle states its own contract in the hint text (`ArrangementPanel.tsx:5148`).
- **Time-range duplicate and consolidation.** `src/commands/timeRange.ts:121` refuses straddling clips and fails closed with an explanatory error routed to the range editor (`src/ui/ContextMenu.tsx:327–337`); consolidation renders a real print and keeps source material intact (`src/commands/timeRange.ts:558–563`), including splitting edge-straddling audio and keeping muted spans (`:637–646`).
- **Marker cue firing at playback.** `src/scheduler/Scheduler.ts:1141–1153` queues cues for markers inside the lookahead window, dedupes per playback session (`:316`, cleared on stop `:546`), and routes a linked audio marker's cue to that clip's track (`src/project-model/markers.ts:33`).
- **Auto-arrange and skeleton.** `src/commands/arrangementShapes.ts:156` builds a seven-slot electronic song form with role fallback cycling, per-section markers and transitions; `createArrangementSkeleton` (`:330`) shares the same builder as the preview (`:331`).
- **Undo is real.** `src/store/ProjectStore.ts:320–385` — every command executed through `services.store.execute(...)` lands on the undo stack (`:369`), no-op commands are dropped (`:357`), and the stack is capped at 256 (`:373`). `src/ui/CommandToast.tsx:17` surfaces the last command label for 1.4 s.
- **Locked clips refuse destructive edits everywhere.** `src/commands/clipGroups.ts:10–15` documents the contract and `assertClipEditable` (`:132`) is the shared guard, called from the command layer for every destructive verb (`src/commands/arrangement.ts:141,168,189,253,368`; `src/commands/audioClips.ts:582,612,706,735,789`; `src/commands/clipEditing.ts:357,533,622,709`; `src/commands/clipPlayback.ts:165,212,247`).

## 5. Open questions

1. **`Ctrl+Shift+C`** (`src/ui/App.tsx:1536`) — is it intentionally private, or an oversight that it is missing from `EDITOR_SHORTCUTS`? It is the only keyboard route to range consolidation and it appears in no help surface.

4. **Is the missing `V`/`C` tool shortcut deliberate?** `src/ui/App.tsx:1559` binds plain `C` and `V` for select/cut, but they are absent from `EDITOR_SHORTCUTS`; the only mention is the CUT button's tooltip (`ArrangementPanel.tsx:5153`).
