**Confidence legend.** `Verified in code/tests` = implementation read plus a second call site or a spec. `Inferred` = implementation read, single call site. `Hypothesized` = plausible from naming only — used once and flagged.

## 3. Candidate findings

### HCP-03-01 — The flagship suite tier has no UI concept at all

**Class:** C (available but poorly explained) → drifts to E.
**Evidence:** `src/effects/definitions.ts:326` defines a 6-member `FLAGSHIP_EFFECT_ORDER`; `src/ui/EffectRack.tsx:137-141` splices it between the 15 core and 36 "MORE" devices; `src/ui/FxAddPopover.tsx:183-197` renders **one flat grid** of 57 tiles showing only `def.name` + blurb + preset count. Searching `src/ui/**` for `flagship` returns only code comments (`EffectRack.tsx:51,152`). The tier word reaches the user only inconsistently through blurbs — `src/effects/blurbs.ts:40,41,67,68` say "Flagship …" for MORPH/VLYX/RIFT/DRIFT, while `:32` says "Vendored PRISM EQ" and `:21` gives REZONANS no tier at all.
**User problem:** PRISM, VLYX, DRIFT, RIFT, MORPH and REZONANS each carry a vendored worklet core and a bespoke editor — orders of magnitude more capability than a single-knob utility — and nothing in the product tells the user that. The only way to find them is to read the grid and recognise a name.
**Minimal intervention:** add a `SUITES` section (or a `★` badge + the word "SUITE") to `FxAddPopover.tsx:183`, sourced from the existing `FLAGSHIP_EFFECT_ORDER` import. No new model.

### HCP-03-02 — The "ALL DEVICES" pro path is documented but no longer exists

**Class:** F (implemented but not correctly wired — stale doc) / E.
**Evidence:** `src/ui/FxAddPopover.tsx:23-24` — _"The old `<select>` list stays available as 'ALL DEVICES' in the rack — the popover replaces the first contact, not the pro path."_ Searching `src/ui/**` for `ALL DEVICES` returns **zero hits**; the only device list in `EffectRack.tsx` is the popover (`:137-141`, mounted at `:406` and `:589`). The popover's search matches `def.name` and the blurb only (`FxAddPopover.tsx:104-105`) — typing `fxeq`, `ultina` or `ozvena` (the internal ids) finds nothing, and so does any word that appears only in a parameter name.
**User problem:** the scannable, type-to-jump list of all 57 devices is gone, and the search vocabulary is narrower than the code's own vocabulary. A user who knows the plugin by its registry name cannot find it.
**Minimal intervention:** extend the query predicate at `FxAddPopover.tsx:104` to also match `type`, and delete or correct the comment at `:23`.

### HCP-03-03 — Sends are post-fader and post-macro, and the UI never says so

**Class:** C (poorly explained) / E (inconsistent with the user's mental model).
**Evidence:** `src/audio-engine/AudioEngine.ts:2171-2175` builds the strip as `input → fx → panner → gain(fader) → modAutoGain(volume lane) → modAutoPan → modMacroGain → modMacroPan → master`; `:2636` taps `nodes.modMacroPan` into each `sendGain`. The send therefore inherits the fader, the volume automation lane, and the macro pan/gain. The mixer hint at `src/ui/Mixer.tsx:645` says only _"How much of this track feeds the {ret.name} return's FX — OFF is dry, 100% fully wet"_ — no pre/post statement. The model has no place to express a choice: `src/project-model/types.ts:275` `sends: Record<ID, number>`.
**User problem:** pulling a fader down does **not** pull the send down. A parallel-compression or "aux reverb as a percentage of the pre-fader signal" workflow silently behaves post-fader, and there is no pre-fader send at all. The user cannot even discover the rule, let alone change it.
**Minimal intervention:** (a) change the `Mixer.tsx:645` hint to say "POST-FADER"; (b) optionally add a `preFader?: boolean` to the send map and a per-return toggle. (a) alone is a one-line fix.

### HCP-03-04 — The send percentage readout contradicts the hint that describes it

**Class:** F.
**Evidence:** `src/ui/Mixer.tsx:646-650` — `value = track.sends[ret.id] ?? 0`, range `0..1.5`, and `format = (v) => Math.round((v / 1.5) * 100) + "%"`. The hint on the same control (`:645`) says _"100% fully wet (up to 150% for pushes)"_. The engine clamps the same 0..1.5 domain (`src/audio-engine/AudioEngine.ts:82` `clampSendLevel`), so v = 1.0 is unity — and the UI prints **67 %** at unity and **100 %** at maximum push.
**User problem:** the number on screen contradicts the sentence under it. A user aiming for a fully-wet reverb reads 67 %, believes they are 33 % short, and over-drives the send.
**Minimal intervention:** format against 0..1 for the 0–100 % band and reserve the top third for a "+PUSH" region, or restate the hint in the same 0–150 % scale.

### HCP-03-05 — Automation can only be created from a MOD-panel dropdown, never from the knob

**Class:** D (available but difficult to activate).
**Evidence:** `addAutomationLane` (`src/commands/automation.ts:34`) has exactly one UI call site: `src/ui/ModPanel.tsx:255`, behind the "+ LANE" button (`:359`) and two `<select>`s (`:289-358`). The slider's own context menu (`src/ui/controls.tsx:484`, rendered `:142`) offers only a typed value and "Reset to default"; the mixer fader menu (`src/ui/Mixer.tsx:740-780`) is the same. The discoverability badge (`src/ui/EffectParameterGrid.tsx:116-125` for knobs, `:75-80` for option params, "AUTO") renders **only when a lane already drives that parameter** — i.e. after the fact.
**User problem:** there is no "is this automatable?" affordance and no "right-click knob → automate". The user must already know that the MOD dock exists, know the parameter's name, and find it in a long `<select>` of every parameter on every device on the track. DAW muscle memory fails completely here.
**Minimal intervention:** add an "Add automation lane" item to the slider context menu (`src/ui/controls.tsx:484`) and to the fader menu (`Mixer.tsx:752`), which already know the track and the param id.

### HCP-03-06 — Nine instrument kinds ship with an empty preset browser

**Class:** B (available but buried) — the bank is absent, so really **I** for those kinds.
**Evidence:** `src/presets/factory.ts:25` `FACTORY_PRESETS` holds 511 presets across 22 kinds. Regex count over the file: `tsar`, `kopa`, `choral`, `ladic`, `hlas`, `strk`, `cink`, `struna`, `dymka` = **0 each**. `src/ui/PresetBrowser.tsx:160` filters the bank by `p.instrument === track.instrument`, so those nine produce an empty list, and `:487` prints **"No presets match."**
**User problem:** these are exactly the nine most distinctive instruments in the product (the hybrid engine, the kick designer, the choir, and six specialised instruments). Creating a TSAR track and pressing PRESETS says "No presets match" — the phrasing of a failed _search_, not of a bank that does not exist. The user concludes the feature is broken.
**Minimal intervention:** replace the `:487` empty state with an instrument-aware message ("No factory presets for TSAR yet") and offer the existing generators (DICE / INTENT) as the alternative path.

### HCP-03-07 — The four deepest flagship suites have zero effect presets

**Class:** E (inconsistent across surfaces).
**Evidence:** `src/effects/presets.ts:38` `CORE_EFFECT_PRESETS` = 206 presets across 50 effect types. Per-type counts: `skrutka` 24, `svFilter` 9, `portal`/`vinyl`/`rezonans`/`kaskada`/`freqShifter` 7 … while `fxeq` (PRISM), `ultina` (VLYX), `ozvena` (DRIFT) and `morphdynamics` (MORPH) are **0**. The rack's PRESETS select only renders when the list is non-empty (`src/ui/EffectRack.tsx:843`), so on those four devices the control simply does not exist, and the ADD-FX tile badge (`FxAddPopover.tsx:186,193`) shows no "N starts".
**User problem:** the devices that require the most setup knowledge are the ones that ship with no starting point, while devices with fewer parameters ship with dozens. The gradient of help runs backwards from the gradient of complexity.
**Minimal intervention:** add a small starting set per flagship (3–5 each) in `src/effects/presets.ts`, or reuse the existing role-landing values (`role-presets.ts:54`) as the seed for the first preset.

### HCP-03-08 — Role-aware landings skip every flagship suite, so their badge never appears

**Class:** E.
**Evidence:** `src/effects/role-presets.ts:54-106` `ROLE_PRESETS` covers 14 types (`vinyl`, `tapeSat`, `svFilter`, `pitchShift`, `beatMangler`, `compressor`, `transient`, `reverb`, `distortion`, `haasWidener`, `bassHarmonic`, `skrutka`, …) — **none** of the six `FLAGSHIP_EFFECT_ORDER` members. `src/ui/FxAddPopover.tsx:187-193` shows the badge only when `rolePresetFor(type, role) !== null`. `src/ui/EffectRack.tsx:131-133` `addLanded` therefore inserts flagship devices with pure factory defaults.
**User problem:** a user who learns the "♪ tuned for 808 / bass" affordance reasonably expects it to apply; on the flagship suites the badge is absent and the device arrives at defaults with no indication either way.
**Minimal intervention:** extend `ROLE_PRESETS` with one row per flagship per role, and/or render an explicit "factory defaults" marker where no landing exists.

### HCP-03-09 — A/B compare exists for five devices and nothing else; there is no chain-level A/B

**Class:** E.
**Evidence:** `src/ui/EffectAbControls.tsx:40` is the generic snapshot controller; it is mounted only at `src/ui/FxEqPanel.tsx:696`, `src/ui/UltinaPanel.tsx:1127` and `src/ui/EffectRack.tsx:1275` (for `morphdynamics`, `ozvena`, `skrutka`). No other effect type renders it, and no snapshot exists at track or chain level — `EffectInstance.deviceState` is per-device (`src/project-model/types.ts` `EffectInstance`), so the whole device chain cannot be A/B'd.
**User problem:** "compare two sounds today" answers differently depending on the device: for PRISM/VLYX/DRIFT/MORPH/TWIST there is a snapshot A/B, for the other 52 types the only comparison is the bypass button (`EffectRack.tsx:944`) and the PRESETS dropdown (`:843`). There is no chain-level or track-level A/B anywhere.
**Minimal intervention:** the command layer already stores an `effect-ab-v1` device state generically (`EffectRack.tsx:1282`) — generalise the control to any effect, and add a chain-level snapshot.

### HCP-03-10 — Master MATCH EQ is a live DSP stage with no manual control

**Class:** F (implemented but not correctly wired to the user).
**Evidence:** `src/audio-engine/masterChain.ts:140-141` declares the stage, `:863` builds four biquads, `:1152-1162` writes the gains from `config.matchEq`. `src/ui/MasteringSignalFlow.tsx:118-119,146-148` reads it and reports only "Corrective bands active" / "Flat · transparent" — a boolean-ish readout with no band values and no control. `src/ui/MasterProcessingControls.tsx:65-348` exposes IN / CEIL / TRIM / TILT / limiter LOOK / REL / TRANS LINK / REL LINK plus tape, M-S, bass-mono, glue, clipper and limiter switches — and **no** match-EQ band control.
**User problem:** the reference-match intent silently moves four filters on the master bus. A user who hears the master EQ change has no way to see the curve, understand which bands moved, or take manual control of a stage that is demonstrably in the signal path.
**Minimal intervention:** render the three/four band gains as read-only sliders in `MasteringSignalFlow.tsx:146`, then expose them as editable controls in `MasterProcessingControls.tsx`.

### HCP-03-11 — "MOD MATRIX" (instrument) and the "MOD" dock panel are different features under similar names

**Class:** C / E.
**Evidence:** the dock tab labelled **MOD** (`src/ui/DockChrome.tsx:82-87`, shortcut `Alt+4`, `src/ui/shortcuts.ts:217`) opens automation/LFOs/macros (`src/ui/ModPanel.tsx:275` `aria-label="Automation, LFOs and macros"`). The instrument **mod matrix** is a completely different thing: `src/ui/ModMatrixRow.tsx:37-110`, reachable only after the Inspector's **ADVANCED** toggle (`src/ui/Inspector.tsx:245-256`, `:407`). The matrix's parameter set is a hard-coded 7 ids (`ModMatrixRow.tsx:7`) and only 12 of the 31 instrument kinds define it (`src/instruments/modmatrix.ts:401`, spread through `src/instruments/definitions.ts`); the other 19 render nothing at all — `ModMatrixRow.tsx:38` returns `null` silently.
**User problem:** a user hunting for "the mod matrix" opens the MOD panel and finds automation; a user on the 19 matrix-less instruments sees nothing at all and cannot tell whether the feature is missing or merely hidden.
**Minimal intervention:** label the Inspector row "MOD MATRIX" instead of the bare `aria-label` at `ModMatrixRow.tsx:98`, and render "no mod matrix on this instrument" rather than `null`.

### HCP-03-12 — Pad-level velocity layers and round-robin are playable but not authorable

**Class:** D / B.
**Evidence:** the model carries them (`src/project-model/types.ts:197` `DrumPad.layers`, documented as _"Disjoint windows act as velocity layers; overlapping windows round-robin"_), the resolver picks the variant deterministically (`src/project-model/groove.ts:60-62`), and the trigger engine plays it (`src/audio-engine/triggerEngine.ts:846`). But every writer outside the model is indirect: DICE randomises it (`src/ui/DiceContext.tsx:749`) and the genre-kit swap installs it (`src/intent/genre-kit.ts:355-382`). The only _authored_ layer UI in the product is track-level (`setVelocityLayersCommand` at `src/ui/SampleBrowser.tsx:448` and `src/ui/Inspector.tsx:346`). `src/ui/KitAuditionBrowser.tsx:21` reads pad layers but never writes them.
**User problem:** a user cannot hand-build a three-velocity kick or a two-hit round-robin snare; they can only accept whatever a randomiser produced. The capability exists in the model, the engine and the export path, and is unreachable by hand.
**Minimal intervention:** a "LAYERS" row in the pad editor that maps a second sample to a velocity window (the `setVelocityLayersCommand` path already exists for the track level and can be reused).

### HCP-03-13 — The legacy inline EffectRack branch is production-dead but still carries a full UI

**Class:** H (dead / unreachable code).
**Evidence:** `src/ui/EffectRack.tsx:109` defaults `mode = "rack"`, and the entire legacy rack JSX at `:574-648` (its own "✚ ADD FX" button at `:578-585`, its own `FxAddPopover` mount at `:589` — a second, divergent ADD-FX surface) renders only when `mode !== "devices"`. All three production call sites pass `mode="devices"`: `src/ui/App.tsx:1714`, `src/ui/MasteringPanel.tsx:455`, `src/ui/MasteringSessionInsertRack.tsx:82`. The branch survives only because specs render the default (`tests/ui/EffectRack.test.tsx:29` and ~20 other cases).
**User problem:** two divergent UIs for one feature; the dead one is the one a code reader (or a future contributor) finds first, and it is the one whose "ADD FX" header button and chain select look authoritative. It also keeps the stale "ALL DEVICES" comment alive (see HCP-03-02).
**Minimal intervention:** delete the `mode="rack"` branch and make `mode` a required prop, or change the default to `"devices"`.

### HCP-03-14 — Device editors page four knobs at a time with no param search

**Class:** D.
**Evidence:** `src/ui/EffectRack.tsx:743-759` splits an effect's params into quick / detail / primary groups and chunks them **four per page**; the pager at `:1288-1307` shows "CONTROLS 1/5" or "DETAILS 2/4" and offers ◀ ▶ only. `src/effects/definitions.ts:1618` `utilityParams` alone declares GAIN, PAN, WIDTH, MONO BASS, PHASE L, PHASE R and more — several pages for a single "toolbox" device. The codebase already owns the pattern for solving this: `src/ui/ModPanel.tsx:280-288` renders a "Filter parameters…" input when the target has deep params.
**User problem:** a user cannot tell that a device has fourteen knobs until they page through five screens, and there is no way to search within a device (the search box lives only in the ADD-FX popover). Deep devices like PRISM hide their real controls behind a bespoke panel instead.
**Minimal intervention:** lift the `ModPanel.tsx:280-288` filter input into the device editor and filter `usableParams` by it, ahead of the page split.

## 4. Verified working (no finding)

- **Effect registry integrity.** 57 `EffectType` members, 15 in `CORE_EFFECT_ORDER` (`src/effects/definitions.ts:303`), 6 in `FLAGSHIP_EFFECT_ORDER` (`:326`), the remaining 36 grouped as "MORE {category}" (`src/effects/registry.ts:4027`); `EFFECT_DEFS` (`registry.ts:3937`) covers every member. Every device's registry params and the panel's param grid are the same list (`registry.ts:2640+` vs `EffectRack.tsx:733`) — no param is defined without a control, and no control exists without a definition.
- **Bypass is honest.** A bypassed effect stays in the chain with a parallel dry path (`src/audio-engine/AudioEngine.ts` ADR-0068 bypass comment near `:86`), so toggling never silences the track; it is a command (`src/commands/tracks.ts:731`) and therefore undoable.
- **Automation targets resolve deeply for the three vendored suites.** `src/project-model/targets.ts:177-208` builds the full `ultina`/`fxeq`/`ozvena` catalogs so macros and automation can address `eq.band3.gainDb`-style ids instead of leaving them dangling; `fxeq` builds 315+ defs per band count and is cached (`targets.ts:168`).
- **Modulation reaches the engine.** `src/project-model/modulators.ts` → `src/audio-engine/automationBridge.ts`; LFOs, steps, gates and mangler patterns are sanitized in `modulators.ts:170-337` and consumed by `src/commands/effectParams.ts` / `effectOps.ts`.
- **The instrument mod matrix is complete and consistent.** The 7 ids in `src/ui/ModMatrixRow.tsx:7` match exactly the ids produced by `src/instruments/modmatrix.ts:401-440`, so no mod param can fall through as an orphan slider.
- **Pad layers are correctly wired for playback.** `src/project-model/groove.ts:60-62` resolves the variant and `src/audio-engine/triggerEngine.ts:846` plays it, deterministically and identically live vs. offline.
- **PDC is correct and per-send.** `src/audio-engine/AudioEngine.ts:2419-2435` sizes track compensation to the longest chain and gives every send its own delay (`:2628-2634`).
- **Group and return routing is complete in the mixer.** Drag-drop _and_ a select assign tracks to groups (`src/ui/Mixer.tsx:486,575`); returns are creatable per strip (`:658-672`) and render their own FX list and meter (`:247-277`).
- **Preset browsing is a first-class surface.** `src/ui/PresetBrowser.tsx` supports query + role/energy/scope filters, live audition with transport-safe stop (`:59-84`), apply and user-preset save with quota-error surfacing (`:123-131`).
- **The SOURCE and ESSENTIAL KIT docks are the best-explained surfaces in the domain.** `src/ui/SourceMacroDock.tsx:135-137` states the pre-condition ("LOAD KICK TO ARM THESE MACROS") and the undo contract ("ONE UNDO STEP") in plain language; `src/ui/EssentialKitDock.tsx:38` labels its role group "Essential kit". These are the pattern the rest of the domain should copy.
- **Ableton-style device reordering is live.** The DEV chain strip supports drag-to-reorder with an insertion index (`src/ui/EffectRack.tsx:496-499`).
