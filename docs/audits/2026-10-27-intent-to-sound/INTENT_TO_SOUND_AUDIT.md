# INTENT-TO-SOUND AUDIT — KYX

**Audit date:** 2026-10-27 · **Repository:** `D:\pulse-forge` (KYX / Pulse Forge) · **Mode:** read-only
**Subject:** the causal chain _Musical Intent → Interpretation → Audio Strategy → Verified Sonic Outcome_
**Question under audit:** _when a user says "make this vocal more intimate without losing presence," can the system understand the goal, identify the audio context, choose a sensible strategy, execute it safely, and demonstrate that the result matches the intention?_

---

## 0. Method, and what this audit did NOT do

**Did:** read the implementation; trace one real request end to end; grep for the absence of capabilities; read the
tests that guard the path; classify every claim by evidence class.

**Did NOT:** modify any code, file, project data, preset, dependency or configuration; run a build, a test suite
or a dev server; **render or listen to any audio**; commit anything.

### 0.1 Evidence classes used throughout

| Class               | Meaning                                                                                                                                                  |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **OBSERVED**        | The implementation was read and the described behaviour is directly readable from it.                                                                    |
| **CODE-SUPPORTED**  | The call path was traced by reading source; it was not executed.                                                                                         |
| **TESTED**          | A test exists that exercises the behaviour. The test was **read**, not run — "a test exists and contains N cases" is the claim, never "the test passes". |
| **DOCUMENTED-ONLY** | Asserted in a doc/ADR but not traced to code.                                                                                                            |
| **HYPOTHESIS**      | A reasoned inference. Never a basis for a recommendation on its own.                                                                                     |
| **UNVERIFIED**      | Could not be established within this pass. Stated as such.                                                                                               |

### 0.2 The audit's own limitations — stated first, because they bound every verdict below

1. **No audio was rendered or heard.** Every conclusion about _audible_ outcome is a statement about _code_. Where a
   conclusion would require a human ear, it is marked for blinded listening (Phase 6 / Phase 7) and left open.
2. **No test was executed.** "TESTED" means a spec exists and asserts the property. A spec that has never been run
   green is not evidence that the property holds. The repository's own gates (`npm run typecheck`, `npm run test`,
   `npm run format:check`) were not exercised in this pass.
3. **Compile-level correctness is unverified.** `tsc` was not run, so a cited line may no longer type-check.
4. **The MCP surface was mapped by name, not by execution.** 40 tool names were enumerated
   (`src/mcp/tools.ts`); the op matrices inside them were read selectively.
5. **Counts quoted in prose** (effect counts, spec counts) were not cross-checked against `docs/CURRENT-STATE.md`.
6. **The architecture changed under the audit, three times, in the product's favour.** The first pass of this audit
   read the intent layer as `mix-idea.ts` + `production.ts` + `effect-intent/`. A deeper pass found the real spine
   (`kyx_intent` → `route.ts`, 41 route kinds), then an unwired strategy layer (`src/ai/bridge/`), then a complete
   contract layer (`src/intent/semantics/`) that implements several of the contracts this audit was asked to
   _propose_. All three are corrected **in place** (§2.1, §2.2, §3.0, §7.7), and §18.3 states the methodological
   lesson. **The report should be read as a starting point, not a closure** — a further pass with a different entry
   point would probably find more.

## 1. Executive verdict

> **KYX's intent-to-sound chain is strong at _execution_ and narrow at _expression_.**
>
> The system will do exactly what it was told, correctly, verifiably and reversibly — and it will **refuse**
> anything it was not told in its own words. The gap between _a musician's language_ and _the engine's
> vocabulary_ is the real boundary of this product today, and it is a **narrowing** boundary, not a broken one.

**The canonical question, answered honestly:** _no._ The request **"make this vocal more intimate without losing
presence"** cannot be executed by this system — and it fails **loudly and honestly**, not silently:

- `intimate` is not one of the 26 production concepts (`src/intent/production.ts:124-151`) nor one of the 3 FX
  goals (`src/effect-intent/parser.ts:13-49`);
- `without losing presence` is an **implicit negation**, and the parser refuses to reinterpret one:
  `parseEffectIntent("not brighter").status === "unsupported"` (`tests/effect-intent.test.ts:71`);
- the result is a refusal with a diagnostic that names the unknown words
  (`src/effect-intent/parser.ts:240-247`) — not a misapplied EQ move.

That refusal is **the most reassuring thing in this audit**. A system that quietly turns "not brighter" into
"+brightness" would be dangerous; this one stops.

**What is genuinely strong (and should be preserved — see §16):**

| Strength                                                                               | Evidence                                                                                                                                                                                                                                                                                                                                                                            |
| -------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A mutation becomes a **verified claim**, not a narration                               | `src/mcp/verified-mutation.ts:90-150` — the choke point corrects the undo claim against the real stack, rewrites "success" as `mutated:false` when the document is byte-identical, and appends a structural read-back when the handler had none. **OBSERVED**                                                                                                                       |
| Constraints are **enforced, not merely understood**                                    | `src/effect-intent/planner.ts:161-164` skips a mapping whose `protects` area is preserved; `:202-207` refuses when the constraint protects every candidate mapping. **OBSERVED** + **TESTED** (`tests/effect-intent.test.ts:491,504,541`)                                                                                                                                           |

**What is genuinely weak (the twenty-two findings are in §11):**

1. **The vocabulary gap is unmeasured and unverified.** The engine accepts a closed vocabulary (26 production
   concepts, 3 FX goals, 41 preserve phrases). The _agent_ speaks open-ended English/Slovak. The translation
   between them is performed by the agent itself and **nothing in the system checks that the translation was
   faithful** — the WHY attached to a step is the literal string `"concept mapping"` / `"assistant curated
mapping"` (`src/mcp/mix-idea.ts:109,209`), not evidence.
2. **The perception layer is rich and mostly unreachable by the AI.** Ultina already computes sibilance, harshness,
   spectral tilt, stereo width, transient density, spectral flux, noise floor, rumble, dynamic range and a 10-band
   profile — and `describeFxMeters` cannot flatten the nested payload, so the agent sees
   _"no telemetry (bypassed, degraded or offline)"_ for a perfectly healthy instance.
3. **FX telemetry is gated on a human having a panel open.** `setFxMetersEnabled` is called only from UI panels
   (`src/audio-engine/AudioEngine.ts:3711`; callers: `src/ui/UltinaPanel.tsx:522`, `src/ui/FxEqPanel.tsx:541`,
   `src/ui/RezonansPanel.tsx:121`, `src/ui/MorphDynamicsPanel.tsx:361`, `src/ui/PortalPanel.tsx:82`,
   `src/ui/KaskadaPanel.tsx:132`). **The AI's perception of the mix silently depends on a human's UI state.**
4. **V3 has no automated coverage at all.** The repository's own test states it plainly: _"No vitest spec in this
   repo renders audio — `renderProject` requires a real `OfflineAudioContext` and every caller of it in the test
   suite stubs it out"_ (`tests/intent-to-audio-chain.test.ts:37-43`).
5. **A 14-strip cap truncates measurement silently.** `STRIP_CAP = 14` (`src/mcp/render-summary.ts:132`), applied by
   slicing (`src/mcp/render-summary.ts:149`, `src/mcp/mix-diagnosis.ts:463`) — the agent is not told its picture was
   cut off.
6. **The best reasoning in the repository is disconnected.** `src/ai/bridge/` holds five whole-mix recipes whose
   headers reason about _why_ a move works and explicitly refuse destructive moves — and an all-or-nothing executor —
   yet nothing outside its own `mockProvider` imports it (§7.7, **F-16**).
7. **The product has two halves that do not share a perception layer.** The AST/AudioSet tagger, the 384-dim
   reference embedding and the learned personal-preference model are reachable from the **generator** and not from the
   **mixer** (§7.7, **F-17**).
8. **"One mechanism per concept" is a deliberate choice, and it has a documented debt.** The production planner says
   so in its own header — _"the planner stays explainable (master doc §15 keeps multi-candidate ranking for later
   phases)"_ (`src/intent/production.ts:739-741`) — and the machinery to pay that debt already exists, wired to
   pattern generation instead of to mixing (§7.3).

**The one-sentence summary of the audit:** _KYX has an unusually trustworthy executor bolted to a
narrowly-understood front end, and the cheapest high-value work is not new DSP — it is making the perception
that already exists reachable, and making the vocabulary that the engine already speaks discoverable to the
agent that has to use it._

A second read of the intent engine found **seven modules that implement, in code, the exact contracts the objective
asks this audit to propose.** They are not a "future framework" — they are the product's own intent contract, and
several are better than what §13 recommended adding.

**Three consequences that change this audit's conclusions.**

1. **The agent-facing catalogue is the intent capability matrix.** `src/plugin-catalog.ts:5` imports
   `buildCapabilityMatrix` — so `kyx_catalog` is built from the _intent_ registry, not only from `EFFECT_META`. §7.4's
   claim that the catalogue comes from the effect definitions alone was **incomplete**, and is corrected there.
2. **The product already tracks, per parameter capability, whether it has human-listening evidence.** The capability
   row carries `metric: "rms" | "centroid" | "crest" | "width" | null` (_"the audibility proxy the readback uses;
   null = honestly unmeasured"_) and `listening: "pending" | "done" | "not-applicable"` — with the comment
   _**"pending is a first-class state, not a pass"**_. **Experiment E-02 in §15 is therefore partly instrumented
   already**: the missing piece is _filling the field in_, not building the instrument.
3. **The model is not translating from nothing.** `src/intent/model-context.ts` assembles a context for the model and
   `src/intent/model-schema.ts` gives it a schema containing `MIX_TARGET_IDS`. F-01's _"nothing in the system checks
   that the translation was faithful"_ is therefore **too strong**: the model is given a typed target vocabulary and a
   context; what is still missing is a check on the _faithfulness_ of its mapping onto that vocabulary.

> **The methodological lesson, recorded because it is this audit's most transferable finding:** two of the three
> subsystems the first pass missed were found by asking **"who imports this?"** — not by reading the obvious entry
> point. A file the size of `src/mcp/tools.ts` (545 KB) cannot be audited by grepping for the symbols you expect,
> and neither can a 174-file intent engine.

## 3. The end-to-end architecture, as it actually runs

### 3.0 Which system is the spine

Three intent systems exist (§2.1). Only one of them is the spine the agent speaks through:

- **A — the router** (`kyx_intent`) is the spine: it is the only entry point that reaches 41 route kinds, the plan
  layer, the model fallback, the destructive gate and the read-back.
- **B — the mix lane** (`kyx_mix_idea`) is a _second, narrower_ lane with a curated goal→parameter table. It is
  the lane this audit traced first, and it is the lane whose vocabulary limits dominate the golden scenarios.
- **C — the AI bridge** (`src/ai/bridge/`) is a third strategy layer with the richest musical reasoning in the
  repository, and it is **not connected to anything** (§7.4).

### 5.2 Goal vs technique — is it distinguished?

**Yes, structurally, in the FX lane.** The engine's contract separates _what the musician wants_ (`goal:
warmth|brightness|space`) from _what a device does_ (`effectType: "eq"`, `paramId: "lowShelfGain"`,
`positiveStep: 0.8`). The mapping between them is a curated table (`capabilities.ts:9-122`), and the rationale is
carried in the plan (`planner.ts:195`, `planner.ts:236`).

**But the mapping is hand-authored and unreviewed** — every one of the 7 mappings says so:
`evidence: "curated-unreviewed"` (`capabilities.ts:24,40,56,72,88,104,120`), and the planner surfaces it to the user
(`planner.ts:214-218`). This is honest labelling, and it is also the **weakest link in the strategy layer**: the
step from _goal_ to _parameter_ is a curated editorial table with no measurement and no listening validation.

### 6.1 The reachability gap — the audit's sharpest perception finding

**The Ultina feature set already contains most of what "intimate" and "presence" would need — and none of it reaches
the agent.**

`src/effects/ultina-core/analysis/assistant.ts:127-192` computes `sibilanceRatio`, `harshnessIndicator`,
`spectralTilt`, `voicedRatio`, `fundamentalRange`, `stereoWidthDb`, `spectralFlux`, `transientDensity`,
`noiseFloorDb`, `rumbleLevelDb`, `dynamicRangeDb` and a 10-band `spectralProfile`. Grep for these in `src/mcp/`
returns **no matches**; the only caller is `src/ui/UltinaPanel.tsx:731`.

The reason is serialization, not absence: `describeFxMeters` (`src/mcp/tools.ts:10426-10449`) prints only top-level
finite numbers and array lengths, and Ultina's payload is `{global, modules, learn}`
(`src/effects/ultina-core/contracts/meters.ts:196-201`) — all objects. The text line therefore degrades to
_"no telemetry (bypassed, degraded or offline)"_ (`src/mcp/tools.ts:6192`) even for a healthy, un-bypassed instance.

**And the meters are gated on a human's UI state:** `setFxMetersEnabled` (`src/audio-engine/AudioEngine.ts:3711`) is
called **only** from UI panels. `src/audio-engine/AudioEngine.ts:1505` calls it _"a PANEL-LIFETIME gate"_. No MCP path
enables it. **The agent's perception of the mix therefore depends on whether a person happens to have the Ultina
panel open.** That is finding **F-02**, and it is the cheapest high-value fix in this audit: one change to
`describeFxMeters` closes rows 4, 6, 8, 9, 16 and 17 of the table above.

### 7.2 Does the system compare alternative strategies?

**In the FX strategy layer: no — and this is a deliberate, documented design decision, not an oversight.**

The production planner states it in its own header:

> _"Folded over effect DEFAULTS (never raw guesses) with the goal amount scaling the primary parameter.
> **One mechanism per concept in v1** — the planner stays explainable (master doc §15 keeps multi-candidate
> ranking for later phases)."_ — `src/intent/production.ts:736-742`

The concept→device mapping is a `switch` with one hardcoded device per case (`src/intent/production.ts:760`):
`"deeper"` → `pitchShift` (`:764`), `"punchier"` → `transient` (`:771`), `"warmer"` → `tapeSat` (`:778`),
`"glue"` → `drumBuss` (`:817`). The parameter values are literal formulas over `goal.amount` — e.g.
`semitones: -Math.round(2 + goal.amount * 5)` (`:765`). There is no candidate list, no score, no alternative branch.

**Two tables, both keyword-driven:**

| Table      | Where                                                                        | Shape                                                                                                    |
| ---------- | ---------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Lexicon    | `CONCEPTS` — `src/intent/production.ts:156-400`, **29 entries**              | `{concept, defaultTarget, patterns[]}` — SK + EN regexes                                                 |
| Recipe     | the `switch` in `planProductionActions` — `src/intent/production.ts:760+`    | one device + literal parameter formulas per case                                                         |
| FX mapping | `EFFECT_INTENT_MAPPINGS` — `src/effect-intent/capabilities.ts:9-122`, 7 rows | `{effectType, paramId, goal, positiveStep, mode, safeMin, safeMax, risk, evidence:"curated-unreviewed"}` |

**Static EQ vs dynamic EQ vs an arrangement change is never compared.** Searching the strategy layer for
`dynEnable|dynEnabled|dynamic EQ|multiband|msEq` returns only two hits, both toggle-id string lists in
`src/effect-intent/catalog.ts:28-29` — no planner ever chooses between them.

**The one place multiple devices are ranked ranks by coverage, not by audio** (`src/ui/fxAddAssistant.ts:34-39`):

```ts
const scored = EFFECT_INTENT_PILOT_TYPES.map((type) => ({
  type,
  covered: goals.filter((goal) => effectIntentMappingsForGoal(type, goal).length > 0).length,

  .filter((c) => c.covered > 0)

```

**In the mastering lane: partially yes.** The planner is handed measurements and rules over them
(`src/mcp/master-assistant.ts:71-265`), and it explicitly _refuses to act_ on a signal it cannot interpret: with an
explicit delivery contract, _"LUFS, crest, stereo and band shares remain report-only because they do not reveal a
safe correction by themselves"_ (`master-assistant.ts:9-13`). That is a rare and valuable form of honesty.

**But:** nothing in the product compares **static EQ vs dynamic EQ vs an arrangement change** for a perceptual
request. The `air`/`deess`/`notch`/`filter` concepts name devices, not decisions.

### 7.3 The comparison machinery that already exists — for the wrong thing

This is the most actionable single observation in the strategy section. **KYX already has a
render-measure-score-reorder loop, and it is wired to pattern generation instead of to mixing.**

`rerankTopBySound` (`src/intent/ranking-v3.ts:60`) renders the top-N finalists, scores them against a genre audio
target, and re-orders them; `scoreCandidatesBySound` (`src/intent/audio-feedback.ts:236`) and
`recordAudioFitObservation` (`src/intent/audio-fit-ledger.ts:131`) are its supporting machinery. Grepping for
those three symbols across `src/` returns only `ranking-v3.ts`, `audio-feedback.ts`, `audio-fit-ledger.ts` and
`pipeline.ts` — **there is no FX-strategy caller anywhere.**

So the asymmetry is exact:

|                         | Choose a _pattern_       | Choose an _FX strategy_                                                              |
| ----------------------- | ------------------------ | ------------------------------------------------------------------------------------ |
| Candidates rendered     | yes                      | no                                                                                   |
| Scored against a target | yes (genre audio target) | no                                                                                   |
| Re-ordered              | yes                      | n/a — one candidate                                                                  |
| Verification            | render-and-score         | `kyx_render_summary` + a human, advisory, after the fact (`src/mcp/mix-idea.ts:252`) |

**The blocker, now answered** (§14.8 has the full reading): `audioTargetFor`'s genre targets
(`src/intent/audio-feedback.ts:40,208`) express **four physical outcome dimensions only** — `rmsRange`, `crestRange`,
`zcrRange`, `bassRange`. They **cannot** express "warm" (no low-mid band), "glue" (a crest reading is a _result_
proxy, not a compression measure) or "wide" (no stereo dimension is scored at all). So C-3 is **not** a small change —
but it is **not a research project either**: the scoring machinery is reusable as-is, and the missing piece is a small
number of extra target dimensions whose measurement primitives mostly already exist (§7.3, §14.8).

### 7.6 Order of operations and gain staging

**Effects are appended, never inserted at a reasoned position.** `addEffect` takes an optional `insertAt`
(`src/commands/tracks.ts:947-958`); when it is absent the instance lands at `initialEffects.length` (`:958`).
`addEffectToTracks` calls it **without** `insertAt` (`src/commands/tracks.ts:721`), so every strategy lane that adds a
device appends it to the end of the chain:

| Lane                 | Call                                                                                | Position                      |
| -------------------- | ----------------------------------------------------------------------------------- | ----------------------------- |
| mix profile          | `src/intent/mix.ts:570` `addEffectToTracks(cursor, [trackId], decision.effectType)` | appended                      |
| assistant device     | `src/mcp/tools.ts:12250`                                                            | appended                      |
| stem mastering ZENIT | `src/mcp/tools.ts:11731`                                                            | appended                      |
| FX assistant (UI)    | `src/ui/fxAddAssistant.ts:61`                                                       | `addEffectWithLandingCommand` |

**No planner in the audited set computes an insertion index.** The only _authored_ orderings are **static preset
chains** — `BEATMAKING_EFFECT_CHAINS` (`src/effects/chains.ts:16-147`), **13** hand-authored chains with an explicit array
order and a one-line `description` each (e.g. `"808 HARMONICS"` — _"Add readable upper harmonics while keeping the sub
centered and controlled"_ — tapeSat → eq, `:17-25`; `"DRUM GLUE"`: drumBuss → compressor, `:101-108`;
`"PHASE-SPECTRAL THROW"`: skrutka → portal, `:44-51`). **These are selected by the user (or by
a named chain id) — no strategy function chooses among the 14.**

`src/effects/fxeq-core/core/signalFlow.ts:31-34` defines an _intra-device_ module order, which is a device's internal
DSP order, not a mix-chain order.

**Gain staging: no before/after accounting anywhere in the mastering planners.** The planner takes measurements and
emits steps; it does not re-measure and does not predict the loudness after. The executor applies the steps and then
tells the caller to re-measure — _"measure again (kyx_loudness) and fine-land with op:trim"_ (`src/mcp/tools.ts:12288`) —
with loudness authority deliberately separated: _"The loudness loop (op:trim) stays the loudness authority"_
(`src/mcp/master-assistant.ts:13`). `src/mcp/stem-mastering.ts:32-53` sets a per-stem ceiling (−1, −1.5, −1 dB) but
**computes no cross-stem sum**.

**The only real gain-staging accounting in the codebase is outside the strategy layer:** `src/audio-engine/metering.ts:163`
(_"One-click export gain staging"_), `src/ui/ExportPanel.tsx:2020,2081`, `src/ui/Mixer.tsx:677` (PRE/POST meter points),
and `src/ui/OzvenaPanel.tsx:255` (_"gain staging stays with the user"_).

**One narrow case where order is respected inside a request:** per-pad (element-level) gain adjustments ride _on top of_
the track FX rather than replacing it (`PAD_CONCEPT_FACTOR` `src/intent/production.ts:102-114`, `padTargets` `:668-672`),
carried separately in `ProductionPlan.padAdjustments` (`:91-97`).

### 7.7 The AI bridge — the best reasoning in the repository, and it is not connected

`src/ai/bridge/` contains **five whole-mix recipes** whose headers carry genuine, specific musical reasoning. The
`punchierDrums` recipe is the clearest example (`src/ai/bridge/recipes/punchierDrums.ts:1-31`):

1. a **transient shaper** on the drum bus — _"the single most direct control over perceived attack"_;
2. a **bus compressor** in `punch` character — _"a fast attack (2 ms) and a short release (120 ms) so it reacts to hits
   rather than riding the whole bar, and the PEAK detector avoids pumping between transients"_;
3. a **high-pass** — _"punch reads better when the kick's sub energy is not fighting the bass"_;
4. and an explicit refusal: _"Deliberately NOT included: swapping the sample kit. That is a destructive,
   hard-to-undo change to the musical content, and the bridge should not do it on an inferred intent."_

That is **better reasoning than anything in the MCP-facing strategy layer**, and it includes a decision about what
_not_ to do — a category the MCP lane has no vocabulary for at all.

Its executor is **all-or-nothing** (`src/ai/bridge/executor.ts`, with `tests/ai/bridge/executor-all-or-nothing.test.ts`)
— exactly the semantics `kyx_batch`'s `atomic` flag lacks (finding **F-06**). Its recipes are matched by regex against
a normalised prompt (`src/ai/bridge/recipes/registry.ts:35-51`), first-match-wins, and a miss becomes an explicit
`no-recipe-match` error rather than silence.

**But it is unreachable.** A grep for `ai/bridge|findRecipe|bridge/executor|bridge/recipes` across `src/` returns
exactly one hit — `src/ai/bridge/mockProvider.ts:18` importing its own registry. The only other importers anywhere are
`tests/ai/bridge/*`. There is no MCP tool, no UI component and no intent route that reaches it.

**Two consequences, and they point in opposite directions:**

- **Risk:** this is a second, parallel way to express "punchier drums" — the recipe (`src/ai/bridge/recipes/punchierDrums.ts`)
  and the production concept (`src/intent/production.ts:171`). If the bridge is ever wired up without reconciling the
  two, the same sentence will mean two different chains. **This is a convergence hazard, not a feature request.**
- **Opportunity:** the bridge's all-or-nothing executor and its per-slot parameter vocabulary are a **ready-made
  answer to F-06** and to the "one mechanism per concept" limitation — if the project decides to use them.

### 8.1 Does "success" mean _applied_?

**Mostly yes, and the mechanism is a single choke point.** `verifiedMutation` runs after the handler and before the
result leaves the surface, so no handler can forget it (`src/mcp/verified-mutation.ts:12-15`):

1. the undo claim is checked against the **real stack** — "one undo step" becomes "folded into the previous undo step"
   when the stack did not grow (`verified-mutation.ts:116-124`);
2. a success with a **byte-identical document** becomes `mutated: false`, `status: "unchanged"`, and the text is
   prefixed _"nothing changed (the document is identical); no undo step — reported: …"_ (`:126-133`);
3. a success with **no read-back** gets a structural one appended (`:134-139`).

**The exception is `kyx_mix`**, whose text is the _plan summary_ rather than committed values
(`src/mcp/tools.ts:7604-7605` region) — so a mix that landed differently reads as "applied". Only
`kyx_plugin_param` performs a true committed-value read-back (`tools.ts:10381-10411`, with a read-back mismatch
downgraded to `partial` at `:10676-10678`). This is finding **F-05**.

### 8.2 The intent lane's dry run — the strongest unused asset in the contract

`kyx_intent` declares `dry_run: true` in its input schema (`src/mcp/tools.ts:1655-1659`): _"Plan only: return the
resolved target, current→proposed values, clamps and warnings without mutating the project."_ The dispatcher passes it
through (`tools.ts:5097`), and `executeIntentTool` implements it (`tools.ts:13014-13030`):

```ts
const route = routeIntentText(trimmed, doc);
const plan = planIntent(doc, route);
return { text, mutated: false, data: { dryRun: true, routeKind, executable, mutates, warnings, steps[...] } };
```

Three properties make this the best-executed part of the contract:

1. **It is deterministic by construction.** The comment is explicit: _"a model fallback is deliberately not
   consulted: a plan must be deterministic and inspectable"_ (`tools.ts:13003-13004`). The agent can therefore always
   ask "what would you do?" and get a reproducible answer — the model cannot make the plan move between two calls.
2. **It returns a machine-readable plan**: `routeKind`, `executable`, `mutates`, `warnings[]`, and
   `steps[{kind, target, parameter, next, note}]` — the `IntentPlan` type from `src/intent/semantics/intent-plan.ts:31-66`,
   with a **typed parameter domain** per step (`linear | log | db | normalized | boolean | none`).
3. **It never mutates**: `mutated: false` is set unconditionally in the dry-run branch (`tools.ts:13014`).

**Why it matters for the audit's central question.** V0 in §9 is _"intent captured → correct target and constraints"_.
The dry run is the only mechanism in the entire product that exposes **V0 before V2** — and it is the only place where
an agent can see the _resolved target_ rather than the _sentence_. The gap is that **nothing makes it obligatory**:
the plan is available, but the write path does not require that a dry run happened first, and the plan's `reason` field
is still a label (`src/mcp/mix-idea.ts:109,209`) rather than a justification. A minimal, non-breaking change — making
the dry run's resolved target part of the _write_ receipt — would turn V0 from "the agent says it resolved correctly"
into "the system says which target it resolved". **OBSERVED.**

## 13. Proposed minimal contract changes and migration risks (Phase 9)

### 13.1 The five conceptual boundaries — what already exists, and what is genuinely missing

The objective asks whether the application needs the boundaries _Intent / Perception / Strategy / Execution / Outcome_.
**The honest answer is that four of the five already exist as concrete, typed code — and that the fifth (Perception)
is the one that is missing, plus a thin Outcome layer.** No new services are required.

**And a correction the first pass of this audit got wrong, in the product's favour:** the Intent Contract is not
"mostly" there — it is **the most thoroughly built of the five**, and it is built in a way this audit had not seen:
`src/intent/semantics/` (§2.2) implements it as **compile-time exhaustive, derived, versioned and cross-product-tested
data**, not as prose or as a hand-maintained table. The perception layer is the genuinely missing one.

### 14.3 What the matrix says in one paragraph

**Everything the audit found as a _missing link_ can be closed with deterministic code and human ears.** The one place a
model is genuinely indicated — semantic labelling of what an audio file _is_ — already ships (the AST tagger), and it is
already off the audio path (a Worker, a 20 s timeout, a circuit breaker). The one place a model is _tempting but
wrong_ is the adjective→parameter mapping, because that step must be **explainable, bounded and reversible** to be
trustworthy at all; a fine-tuned model would make it none of those three.

### 14.8 The `audioTargetFor` precondition — **ANSWERED**

**Question:** can `audioTargetFor`'s genre targets express _perceptual_ FX goals ("warm", "glue", "intimate"), or only
genre-level pattern targets? **Answer: no — and the precise reason makes C-3 cheaper than it looked, not harder.**

`GenreAudioTarget` (`src/intent/audio-feedback.ts:27-36`) has exactly **four** dimensions, and `scoreAudioFit`
(`:180-201`) is a **range-fit** function: 1.0 inside the range, linear falloff outside, averaged over the four.

| Dimension    | What it measures                         | Which perceptual goal it can express                                                                                                            |
| ------------ | ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `rmsRange`   | integrated level                         | _loudness_ — yes                                                                                                                                |
| `crestRange` | _"dynamic range proxy"_                  | _punchy_ — **partially**: crest is the **result** of compression, and a low crest is equally consistent with glue, a limiter, or a dense master |
| `zcrRange`   | _"brightness proxy"_ (spectral centroid) | _brighter / darker_ — yes, along the centroid axis                                                                                              |
| `bassRange`  | low-band energy ratio                    | _bass-heavy_ — yes                                                                                                                              |

**Three concrete gaps, and this is the useful part:**

1. **"Warm" cannot be expressed.** Warmth is a **low-mid band** property; `zcrRange` moves along the **centroid** axis.
   A warmer mix is a _darker centroid_ with an _unchanged_ centroid-heavy band — the two goals are not the same
   direction. There is no band-resolved dimension in the target.
2. **"Glue" cannot be expressed.** `crestRange` is a _result_ proxy, not a measure of compression behaviour; nothing
   in the target distinguishes "glued" from "limited" or "dense".
3. **Width is measured and then thrown away.** `scoreCandidatesBySound` calls `extractStereoAudioFeatures(left, right)`
   (`:278`) and returns `stereoFeatures` in the result (`:289`, typed at `:216`) — but `scoreAudioFit(features, target)`
   (`:285`) is called with the **mono** features only, and `GenreAudioTarget` has no stereo dimension. **The stereo
   measurement is captured and never scored.**

**Two more facts that make C-3 an engineering task rather than a research project:**

- **The targets are partly measured, not hand-written.** `audioTargetFor` prefers `GENERATED_AUDIO_TARGETS` — measured
  from full reference renders — over the hand-written table, falling back to `house` only for out-of-union genres
  (`:208-210`).
- **The cost model is favourable.** Candidates render **in parallel, each in its own `OfflineAudioContext`**
  (`:245-247`), so the audio-fit stage costs the **slowest** render, not the sum. And the audio contribution is
  deliberately bounded: `AUDIO_FEEDBACK_WEIGHT = 0.3` (`:177`) — the measured fit is **30 %** of the final ranking,
  the symbolic rank **70 %**.

**So the verdict on C-3 (candidate mechanisms) is:** the _mechanism_ is reusable as-is, the _target vocabulary_ needs
**two to three extra dimensions** — a band-resolved warmth axis, a compression/pumping proxy, and a stereo-width
dimension whose measurement primitive (`extractStereoAudioFeatures`) already exists but is unused — and the scoring
function needs to accept a dimension set instead of four fixed fields. **That is a contained change with a named
prerequisite, not a research project.** The prerequisite it _does_ create is a calibration question: what range
counts as "warm" for a given genre? That is a listening question, and it belongs to E-02's panel.

**One more honest detail:** a candidate whose render **fails** is silently skipped (`catch { return null }`,
`:292-295`) — it simply receives no audio score, with no diagnostic. That is a fail-soft behaviour consistent with
the rest of the codebase, but it means a broken render silently changes the ranking rather than being reported.
**OBSERVED.**

### 14.9 Why no fine-tuning is recommended — and the preconditions

Fine-tuning a model to map musical adjectives onto DSP parameters is the obvious proposal for gap #3, and this audit
**does not recommend it**, for four reasons that are specific to this codebase rather than generic:

1. **The target is already a table.** The 7 mappings exist with explicit bounds, explicit risks and an explicit
   `evidence: "curated-unreviewed"` label (`src/effect-intent/capabilities.ts:9-122`). A model would replace a
   _readable, editable, reviewable_ table with an opaque one — losing the property the code explicitly chose
   (_"the planner stays explainable"_, `src/intent/production.ts:739-741`).
2. **The failure mode is worse.** A wrong table entry is visible in the plan and correctable by a human; a wrong model
   output is invisible until someone hears it.
3. **There is no baseline.** No measurement of the current mapping's accuracy exists, so "the model is better" is not
   a testable claim today.
4. **There is no dataset.** The listener data does not exist yet — E-02 has to produce it first.

**Preconditions before any fine-tuning proposal is even discussable:** (a) E-02 has produced a golden set with
measured human agreement; (b) the current table's error rate is quantified; (c) a target metric exists with a
regression budget; (d) the model can be _shown_ to beat the table on that metric, with the table as the control.

### 16.5 The single most important thing to preserve

**The refusal culture (§16.2) is the product's safety property, and it is more valuable than the ability to say yes.**
Every widening of the vocabulary proposed in §17 must keep it: a new word must be added as a _recognised_ concept with
a bounded, reviewable mapping — never as a way to make an unsupported request silently succeed. The engine's ability
to say _"I don't know that word, and here is exactly what I do know"_ is what makes an agent-driven DAW safe to hand
to a model.

### 17.7 The auto-apply budget — a question this audit can answer

A product question was carried into this audit: **is a fixed count of automatic applications per session the right
budget?** The audit's answer is that **a count is the wrong unit**, and the codebase already contains the right one.

- The mix lane applies **one idea as one snapshot** (`src/mcp/mix-idea.ts:226`) — the whole request is one undo.
  That is the correct unit: **a musical decision**, not a count of parameter writes.
- A request that needs three devices still gets one undo, because the count of _devices_ is an implementation detail
  of one decision.
- The budget that actually matters is therefore: **how many musical decisions may the agent take in one turn without
  asking?** The current design answers that structurally — one intent = one snapshot = one undo, and the agent must
  call the tool again for the next decision.

**Recommendation:** keep the decision as the unit, and cap **the number of decisions per turn** rather than the number
of writes. A cap of 10 _writes_ is arbitrary (one de-esser can be 3 writes; a master chain can be 8), whereas a cap of
**2–3 decisions per turn** maps to what a musician would actually accept from a suggestion without reviewing it. The
current code already enforces the right thing structurally; what it lacks is an explicit statement of the rule.

### 18.4 The single question this audit leaves behind

> **KYX's executor is trustworthy, its perception is rich but mostly hidden from the agent, its strategy layer is a
> single-candidate keyword table, and its measurement layer cannot yet prove that anything changed.**
>
> The three cheapest moves — flatten the meters, carry the resolved target, make the measurements a pair — would
> close more of the gap than any new model, any new DSP, or any new service. The expensive move the team is most likely
> to want — fine-tuning a model to understand "intimate" — is the one that should wait until a baseline and a
> listening panel exist, because without them it cannot be evaluated and therefore cannot be trusted.
