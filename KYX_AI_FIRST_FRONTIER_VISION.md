# KYX: The AI-First Beat Production Workstation

**Frontier vision, musical intelligence, architecture and experiment portfolio**  
Research date: 28 October 2026, Europe/Bratislava. Repository anchor inspected: `5641f755`; the shared checkout may advance independently. Research artifact only: no implementation, installation, runtime launch or test execution was performed for this study.

## 1. The KYX that should exist in three years

KYX should be the instrument in which a producer can grab the _relationship_ between musical parts, bend it, hear three convincing possibilities, and keep exactly the pieces that make the track theirs. “Make this bass answer the kick, preserve my snare pocket, and make the next eight bars feel larger without raising the master” becomes a visible, playable musical experiment: protected notes stay protected, alternatives share an identity, their differences are audible and inspectable, and accepted decisions remain editable. The workstation remembers confirmed artistic commitments rather than inventing a story about the artist. Its intelligence lives in the connection between intention, musical structure, sound and human judgment. The category ambition is an **auditionable musical decision environment** whose output is an authored project, with a beatmaker's immediacy and a production system's trustworthiness.

## 2. Research method, evidence and limits

### Evidence vocabulary

- **Observed (O):** directly inspected file contents, artifact sizes, manifest declarations or tool wiring. This is observation of repository material, not a listening test.
- **Code-inferred (CI):** behavior traced through connected implementation paths, without executing them. Confidence is high for local logic, lower for cross-device behavior.
- **Reasonable assumption (RA):** a planning premise that needs validation, such as a small team or three alternatives being manageable.
- **Research hypothesis (RH):** a falsifiable claim about musical or workflow benefit.
- **Speculative frontier (SF):** an ambitious possibility lacking sufficient evidence for a delivery commitment.

All new designs below are proposals, marked RH unless otherwise stated. Horizons are resource allocation proposals, not release promises. Numerical latency targets, experiment thresholds and costs are prospective. No reported repository test count, model benchmark, browser verification claim or listening outcome was reproduced here. A manifest's evaluation is evidence of a recorded evaluation claim, not proof that a feature succeeds in this session.

The repository has unusually large documentation tables; some broad terminal reads were truncated. Findings below use the targeted source and manifest inspections listed in the evidence index. Documentation is not treated as an exhaustive verified inventory. `ARCHITECTURE.md` includes future WASM language; `AGENTS.md` explicitly says there is no shipped Rust/WASM DSP path. ONNX Runtime using WASM for inference is a different matter.

### Strengths to amplify

The most valuable existing assets are the editable project model, command system, deterministic generation fallback, shared renderer, explicit brief constraints, and new evidence boundaries. Together they allow a meaningful creative loop without a frontier model. Reuse them before building orchestration infrastructure. Preserve the existing timeline as the interoperable substrate; no project-schema revolution is required for the first prototype.

### Production spine: assets, recovery and authority

O/CI, high for the local contracts [R16,R19]: `.kyx` export serializes the document; import is shape-based rather than extension-dependent, applies a 10 MiB file ceiling, validates and migrates. This is portable project structure, not proof that external sample bytes are embedded. A proposal receipt must therefore retain asset identities and disclose unresolved external dependencies. The sample manifest already models category, tags, mood and redistribution-license variants; contextual retrieval can build on these fields rather than require neural tagging for everything.

Stem export preserves parent group tracks when selecting source tracks, and deliberately clears live mute/solo state in its deliverable project. This is a concrete example of why “render the selected tracks” has semantics beyond filtering IDs. A solo analysis stem, an export stem and the mix heard through all returns need separately named signal stages. Preset/sample preview in the browser is useful existing UX, but no claim is made that all such previews already use the arrangement context.

Save lifecycle code distinguishes asynchronous IndexedDB persistence from synchronous last-chance recovery hooks. `pagehide` and `beforeunload` trigger best-effort flushes; the comments correctly acknowledge that a browser can terminate before asynchronous persistence completes. The autosave debouncer adds bounded defer behavior so sustained gestures do not indefinitely postpone writes. These are valuable defenses, not a promise of lossless recovery. New proposal caches should be disposable; accepted music and durable user-confirmed decisions must enter the established save path. Crash/reopen tests belong beside preview/undo tests before promising a new authorship workflow.

The MCP structural verification helper checks what landed instead of trusting the action's requested label. Scope guards distinguish declared writes from actual diff paths and disclose unverifiable scope. Trust/permission handling is a separate boundary from sound judgment. Direct editor commands, AI proposals, tool approval and post-write structural evidence should remain explicit concepts; a generic “AI approved” flag cannot replace them. The intent router also contains concrete clarification paths for contradictory level directions or missing targets. Preserve those abstention behaviors when adding more fluent interpretation.

## 3. What traditional DAW mental models get wrong for beats

This is a design critique, not a claim that every competing DAW lacks the feature.

1. **They make relationships indirect.** A producer wants the bass to leave room after the kick, but edits notes, envelopes and sidechain controls separately. KYX should present a relationship and multiple ways to realize it.
2. **They make experimentation destructive or administratively expensive.** Duplicated tracks and clips lose the question that motivated them. A counterfactual should preserve its parent, constraints, audition and selective merge.
3. **They equate the visible grid with musical identity.** Pocket also lives in articulations, accents, sample attacks and phrase position. Moving MIDI alone may not preserve perceived timing.
4. **They hide the cost of alternatives.** More sounds, plugins and generated candidates can consume attention and CPU. A creative environment should have an explicit alternative budget.
5. **They separate composing from mix consequences.** A shorter bass note can create space more convincingly than adding another compressor. KYX should audition both causal interventions.

Competitive caution: Ableton already offers selected-note transformations and scale-aware generators; Bitwig Operators can expand variation into editable events; Cubase 15 includes melodic pattern tools and chord assistance. These are real baselines, not straw men. KYX's possible differentiation is the _connected loop_ of contextual constraints, musical relationships, playable alternatives and explicit outcome evidence. See external sources S01–S03.

### The common record proposed for experiments

```text
MusicalProposal v1 (design sketch, not an implemented schema)
  base: projectId + revision + content hashes + sample/engine versions
  scope: stable track/clip/event IDs + [startTick,endTick) + tempo-map hash
  intention: explicit requirements | preferences | unknowns
  evidence: IDs + origin + stage + range + version + uncertainty
  invariants: predicates with hard/soft status and user ownership
  candidates[0..2]: seed + generator version + typed delta + changed IDs
  checks: structural | acoustic | subjective, each with its own result
  audition: source/candidate hashes + render settings + match gain + validUntil
  resolution: accept all | accept fragment | reject | defer; optional reason
```

This is a wrapper around commands, not a replacement project model or live model dependency. A seed alone cannot reproduce remote model output: store the accepted typed delta and relevant asset hashes. Floating DSP and external instruments can still need captured audio for exact recall.

For example at 120 BPM, 4/4, PPQ 480, a sixteenth is 120 ticks or 125 ms. A kick at ticks 0 and 960 and bass at 0, 720, 960, 1440 can produce alternatives with bass starts at 60 and 1020 (62.5 ms after each kick), or unchanged starts but shorter releases. A 12 ms hat offset is about 11.52 ticks at this tempo: storage quantization must be disclosed if it cannot represent that precision. These are illustrative edits, not tested sounds. Tempo changes require integrated time mapping, not a global tick-to-ms multiplier.

## 6. Five signature journeys

### J1 — “Keep the pocket; untangle kick and bass”

**Input:** select bars 9–13 and the kick/bass tracks; choose “more separation,” lock snare/hat event IDs, retain all samples. **Interpretation:** “separation” remains a preference; low-band coincidence is evidence, never a masking verdict. The user chooses whether timing changes are allowed. **Control:** maximum bass onset movement 60 ticks, maximum duration reduction 25%, no master/track gain increase, one existing-envelope change allowed.

**Alternatives:** A delays two bass attacks; B shortens two notes; C changes the existing amplitude release. The UI ghosts note changes and shows parameter units. Each has an unmodified source button. **Audition:** render the selected passage with lead-in and tail, full routing context; keep raw gain facts and separately apply monitoring match gain. Warm playback switches only after audio is ready and at a musical boundary.

**Verification:** exact locks and scope first; true-peak/headroom and onset-aligned low-band descriptors second; producer preference third. A proxy may worsen while the producer prefers the sound. Accept B as one command, retain the question and chosen delta; reject A/C explicitly or discard without a taste vote. **Failure:** ambiguous kick source asks for selection; unavailable rendering leaves a symbolic proposal marked unauditioned; revision change expires previews. **Undo:** restores B's previous notes and envelope data atomically; any cached future audition must be invalidated.

### J2 — “A darker eight-bar beat, my drums untouched”

**Input:** prompt or a mood tile on a selected region. **Interpretation:** show hard requirements (eight bars, existing drums, D minor if explicitly set), preferences (“darker”), unknowns (lower register versus less brightness). Choose one audible example to clarify instead of asking for a long description.

**Control:** current kit only; bass/chords allowed; two instrument instances maximum; no master gain move. **Alternatives:** same drum identity, three bass/chord relationships, displayed as three family tabs. **Verification:** protected drum events/assets compare exactly; scale/register, note bounds, CPU budget check independently of style preference. Audition matched source/variants. **Failure:** key ambiguous → preserve existing pitches or ask; small model unavailable → deterministic alternatives with disclosure. **Undo:** one transaction per accepted family, no hidden replacement of protected patterns.

### J3 — “Make the drop feel bigger, with the same peak ceiling”

**Input:** select two user-labelled sections, draw restraint then release on a contrast lane. **Interpretation:** no automatic assertion that either section is a chorus. Offer density, register and texture as separate axes; peak ceiling is a hard measured requirement with a stated render margin.

**Alternatives:** A removes preceding hats and adds a one-bar anticipation; B opens chord voicing at entry; C changes articulation using existing instruments. **Control:** preserve bass pitches, forbid new assets and master processing. **Verification:** source/variant transitions rendered in context, peak ceiling checked, loudness matching used only for comparison; the arrangement can naturally change loudness within the peak limit. Listener decides perceived payoff. **Failure:** ceiling fails → revise or show infeasible; never add an undisclosed limiter. **Undo:** accept only voicing changes if desired; re-render the selective merge before commit.

### J4 — “Find the kick that belongs in this loop”

**Input:** hold a sample-browser modifier to audition an allowed replacement in place. **Interpretation:** compare transient/decay/register descriptors and kick/bass interaction, not a universal “best kick.” **Control:** current local/licensed library, maximum three suggestions, tune adjustment opt-in, loudness compensation for monitoring shown separately from project gain.

**Alternatives:** tight/punchy, round/sustained, contrasting texture; allow “none” and ordinary browsing. **Verification:** import/decode and playable range checks; full-loop matched audition; peaks checked after any actual gain choice. **Failure:** no convincing candidates → keep original and show why search was restricted; missing asset never becomes a silent substitute. **Undo:** restores exact asset ID and any accepted tuning/gain delta. Downloaded files remain separately managed library assets.

### J5 — “Continue yesterday's strange groove”

**Input:** reopen and select “continue this family.” **Interpretation:** display confirmed commitments: late ghost snare pinned, bright hats explicitly rejected in this scope, source seed and accepted edits. Do not infer reasons from elapsed time. **Control:** choose allowed novelty axes and four-bar mutation rate, preserve the accident from C21.

**Alternatives:** three related 16-bar evolutions with event-level ancestry; reveal only changes on audition. **Verification:** locked timing/velocity preserved; repeated-event identity and variation distribution measured; musician judges family resemblance. **Failure:** parent assets missing → relink before render; imported project has no memory → say so; preference evidence too sparse → default to neutral ranking. **Undo:** reverting the accepted branch does not delete the parent or rewrite history; forgetting preference data is a separate explicit action.

### Where actual listening is essential

Symbolic data is sufficient to prove an event did not move, count density, inspect harmony candidates and explain planned changes. It cannot prove that a long kick tail masks a bass, that a distorted patch sounds harsh, that a compressor pumps, or that a transition feels satisfying. Those need rendered audio; artistic conclusions additionally need a listener. Source separation is optional when project stems are directly renderable. Avoid inferring stems from a mixture when the project already contains the source tracks.

For a 4096-point spectrum at 44.1 kHz, the frame spans about 92.9 ms and bin spacing is about 10.77 Hz. The existing kick/bass method therefore gives useful coarse low-band evidence but cannot reliably resolve arbitrarily close fundamentals or establish psychoacoustic masking. Increasing FFT size improves frequency resolution while smearing timing; zero padding does not add information. Report this trade-off in the UI only when it matters to a finding.

### Confidence should drive behavior

Use separate fields for observation quality, model uncertainty and proposal preference. A deterministic measurement may be exact under its declared signal stage while its musical interpretation remains weak. Estimate calibration with held-out reliability diagrams and selective risk/coverage curves. A low-confidence downbeat should trigger phase alternatives or user confirmation, not an elaborate confident explanation. Multiple models agreeing on a biased dataset does not substitute for ground truth.

### Concrete engineering contracts and boundaries

**Scope.** Capture selection explicitly, using existing project IDs and half-open tick ranges. Record meter, relevant tempo-map segments, source offsets/warps and whether a clip references a shared pattern. Editing a shared pattern can affect other clips: default to making that consequence explicit, not assuming selected occurrence means global pattern edit. Re-resolve IDs and base revision at commit. Scope expansion requires a new preview.

**Constraints.** Start with finite predicates: locked event fields, immutable asset IDs, permitted parameter target-instance tuples, onset forbidden intervals, maximum edit count, note/register bounds and no master-gain move. Hard failures remove a candidate; soft scores remain visible trade-offs. Acoustic ceilings need a rendered check with defined measurement method and tolerance. A model cannot waive constraints or convert “no new samples” into “similar replacement.”

**Preview.** Clone the project; use R04 rather than a simplified synthesis path. Include preroll for envelope/delay/compressor state and enough tail; document where the current 0.6 s preview tail is inadequate. Analyze the requested passage, but render required context. Stateful effects and sidechains mean rendering just the isolated target can be misleading. Do not store monitoring loudness compensation as a project gain unless the user accepts that change separately.

**Commit and undo.** Stable typed deltas compile to existing commands. Recheck base revision and locks, then one atomic transaction. Unknown revisions require content comparison; unknown freshness must be disclosed. Partial merge requires dependency checks and a new preview. Proposal generation never writes the live project; project commands remain the authoritative mutation boundary.

**Caching.** Key symbolic results by relevant source hashes, scope, tempo map, seed and generator/schema version. Key renders additionally by asset bytes, routing/FX/automation, engine version and render settings. Conservative project-revision invalidation first; graph-local invalidation only after correctness evidence. Cache failure/absence briefly, not indefinitely. Missing files or quota eviction invalidate audition readiness. Limit audio cache bytes and expose clearing controls.

**Latency budgets, proposed not measured:** UI acknowledgment ≤50 ms; event-delta preview p95 ≤150 ms on the middle device; ready cached A/B switch at the next chosen boundary; cold analysis visibly queued with estimate/progress and cancellation; a four-bar contextual render target p95 ≤2 s on the middle device, with ≤8 s on a low-tier device or degraded symbolic mode. Optional deep interpretation target ≤10 s warm; no promise if loading a model. Existing 20/60 s embedding ceilings must never silently become routine audition delays.

**Resources.** One bounded analysis queue per session initially; prioritize playback, then user-triggered preview, then background indexing. Worker execution still competes for CPU/cache/memory. Pause speculative jobs during recording, underrun indications or thermal pressure; cancel obsolete generations. Cap candidate count and PCM buffers before optional model quality. Treat `deviceMemory` as a hint, not a portable capability guarantee. Existing lean budgeting [R05] is a useful start.

**Models.** Keep small ORT WASM models and their fallback paths. A common runtime version/binary mapping matters more than simply replacing WASM with WebGPU. Optional heavy models have explicit download size, license, hash, storage and backend requirements. The stem manifest's failed WASM path is an actual warning against assuming universal fallback. For cloud tools, send only selected evidence/audio after explicit user intent, with retention policy; the base DAW must keep functioning offline.

**Provenance and telemetry.** A receipt distinguishes structural success, observed acoustic change and user verdict. No single `success: true` should conflate them. Log opt-in local timing/error/edit-validity statistics without raw audio/prompts by default. Keep reproducible artifact IDs, not verbose private chains of thought. Export/forget tools need tests. Model output and audio metadata are untrusted data, never authority to change permissions.

**Browser reality.** The Web Audio 1.1 working draft describes a default 128-frame render quantum, with configurability; neither that draft nor an interface timestamp proves the timing behavior of all KYX voices or browsers. ORT documents require compatible runtime/binary versions and cross-origin isolation for WASM multithreading. WebGPU needs capability and operator-path checks, and its GPU resources can contend with UI/rendering. Do not promise browser-wide real-time AI. These are deployment constraints, not reasons to place inference in an AudioWorklet [S04–S07].

## 9. AI-first UX principles grounded in production

1. **Attach the action to the musical thing.** Region, pad, selected notes and two-part relationship tools are primary. A small prompt field is optional for complex questions.
2. **Make interpretation editable before work begins.** A compact row of “keep / may change / uncertain” is more useful than a confident paragraph. Presets of constraints accelerate experts.
3. **Explain with sound and differences.** Show the two bass notes that moved and the tail that shortened; let the producer hear each causal alternative. Evidence IDs support details on demand.
4. **Limit alternatives by default.** Source plus three distinct strategies beats twenty tiny variants. “None” is valid; no endless regeneration funnel.
5. **Keep accepted content ordinary.** Notes, sample assignments and parameters remain editable in their existing editors. The AI wrapper never becomes a required proprietary playback object.
6. **Separate proof from judgment.** A protected-snare check can pass; low-band overlap can decrease; the artist can still dislike the result. All three may be simultaneously true.
7. **Keep gestures fast.** A drag should preview a cached transform or acknowledge pending work. Keyboard: select, invoke, source/A/B/C, accept fragment, undo. Mouse: region handle and ghosts. Performance: prepare alternatives ahead of time and switch at a known boundary.
8. **Teach through bounded examples.** Beginners can choose “shorter bass” versus “later bass”; experts can inspect exact ticks, envelope values and measurement stage. No forced tutorial or hidden global automation.
9. **No silent writes or fake availability.** Unavailable model/render yields an honest degraded state. A stale audition is visibly expired. Existing deterministic hotkeys stay direct.
10. **Authorship has priority over convenience.** User labels and protected accidents outrank inferred song roles and generic style priors. Explicitly confirmed memories have scope and can be forgotten.

### Reliability attacks that must survive

- **Models disagree:** keep hard constraints deterministic; expose distinct musical hypotheses instead of averaging incompatible actions. A held bass versus staccato bass is an audition choice.
- **Ambiguous instruction:** state the uncertainty and show one or two controllable axes. “Harder” never authorizes an unspecified gain increase.
- **Inference dies or internet disappears:** existing project playback/editing continues; parser/finite transforms remain; unavailable optional capability is visible.
- **Weak device or dense session:** reduce speculative candidates, defer audio jobs and reuse renders. A CPU worker is not free merely because it is off the UI thread.
- **Undo after another edit:** undo semantics follow the command stack; a proposal cannot restore an old whole-project snapshot over unrelated later work. Preview expiry and transaction policy must be explicit.
- **Automation changes a proposed parameter:** inspect effective automation in scope; either propose a compatible automation edit or refuse the ambiguous write.
- **Shared patterns or sends:** a selected clip can have wider consequences. Show dependency scope and re-render the combination; no hidden global changes.
- **Replay after model update:** persist accepted deltas/assets; pin engine/model version for regeneration. Provider name and seed are insufficient.
- **Preference proxy gaming:** optimizing low-band overlap, embedding score or next-note accuracy can make music worse. Keep listener decisions independent and audit diversity.

### Ideas to reject now

1. **One prompt to a final flattened instrumental as the core product.** It sacrifices editability and makes KYX compete on expensive external model quality. Optional texture assets may be useful later.
2. **An always-running agent that fixes the mix while the producer works.** It races human edits, burns resources and obscures authorship. User-invoked, scoped proposals have a stronger trust model.
3. **Universal “professional sound” scoring.** Cultural preference, intentional distortion and genre diversity make a scalar quality claim misleading. Offer named measurements and optional personal preferences.
4. **LLM-generated arbitrary DSP code or audio-thread inference.** Reliability, timing and auditability lose to validated native controls and offline generation.
5. **A giant conversational control panel as the main instrument.** Routine beat work is faster through notes, pads, handles and audition. Conversation remains useful for complex intention.
6. **A new universal graph replacing tracks, clips and plugins immediately.** Schema migration, playback risk and maintenance exceed evidence of benefit. Add lightweight relationship records above current objects.
7. **Mandatory full neural stem separation before assistance.** Project sources are often already available, and the observed stem fallback can fail on WASM. Render direct stems first.
8. **Exact living-artist imitation as differentiation.** It creates rights, trust and homogeneity problems and says little about a musician's own authorship. Describe musical attributes and use authorized references.
9. **A model for every deterministic control.** Swing, envelope drawing, exact constraints and timeline diffs usually deserve ordinary algorithms.

## 12. Differentiation and durable product advantages

The moat is a coherent set of contracts and experiences: authored project data grounds musical evidence; relationships yield bounded alternatives; those alternatives are heard quickly; accepted decisions remain ordinary editable content; explicit local feedback improves future offers. Individual models and chat interfaces are replaceable. A compact suite of reproducible musical interaction evaluations and well-designed deterministic primitives is harder to copy than a prompt template.

This is a **strategic hypothesis**, not a validated defensibility claim. Local availability, owned/editable project output and a musician's confirmed preference history can lower switching friction _within the product_, but KYX should retain export and forgetting; trapping users is not the value proposition. Avoid a data-network-effect story until consented data volumes and actual performance gains exist. Raw private audio is not needed to start building this advantage.

Fresh primary-source checks show overlapping incumbent tools [S01–S03]. They do not establish that no competitor has a grounded relationship loop. Before saying “first,” “only,” “best” or publishing a category claim, perform hands-on competitor tasks with the same pocket/contrast/merge scenarios, a dated feature matrix and measured latency/quality. This study does not make those claims.

For a small team, sound quality and workflow cohesion are the strategy: choose one four-bar relationship loop, make it trustworthy and delightful, then expand to sections. Do not simultaneously fund new plugin ecosystems, a vocal-first product, a proprietary foundation audio model and a new general DAW ontology as prerequisites. Full-DAW scope remains legitimate under ADR 0014; the differentiated product wedge is instrumental beatmaking.

### The three investments

1. **A shared Musical Proposal and Evidence boundary** extending R06/R10/R11: one scope, hard constraints, typed deltas and independent structural/acoustic/subjective outcomes. This is the **enabling platform primitive**. It must replace duplicated adapters incrementally, not become a parallel command runtime.
2. **Pocket Negotiator**, beginning with selected kick/bass and three finite intervention strategies. This is the **flagship experience**. It forces the platform to earn its complexity through sound.
3. **Fast contextual audition with identity-preserving families**, starting with source plus two/three variants and exact anchors. This is the human interaction advantage; the same mechanism later supports C05 and C07.

Opportunity costs: defer broad arrangement agents, generalized transcription, heavy semantic audio packs, cloud orchestration, an expansive preference-training program and unrelated instrument/effect proliferation. These investments consume at least the same engineering capacity while weakening the ability to validate the flagship.

### H1: 0–90 days

Planning assumption: two engineers with part-time producer/research support, about 18–22 net engineer-weeks available after support work. If only one engineer is available, halve the scope: finite Pocket Negotiator plus receipts, no new learned model. External testing allowances follow experiments, not a fixed launch spend.

Reserve roughly 25% of the 90-day capacity for scheduling/render correctness, failure recovery and usability iteration. A late failing correctness gate reduces feature scope rather than weakening the gate. H1 success can be one excellent four-bar interaction; it does not require 24 concepts.

### H2: 3–12 months

Sequence C07 family variation and C05 contextual selection after the audition primitive is proven. Add C03 groove transfer only after phase/attack evaluation; add C04/C16 section contrasts after family identity and multi-clip dependency handling. Run E07–E11 selectively. Persist decision records only after ephemeral prototypes stabilize, using proper schema migration and bounded storage.

Optional deeper reasoning gets a small, provider-neutral adapter only when complex requests demonstrably fail deterministic interpretation and better interpretation improves musical outcomes. It consumes the same context schema, cannot execute directly, and is evaluated against A. Preferences remain explicit and local; opt-in learning requires held-out benefit. Maintain CPU/offline paths as primary supported modes; GPU packs get separate measured support matrices.

### H3: 12–36 months

Run C24 identity-boundary research (E14) with a small isolated budget. The bet is that a producer can teach a compact representation of “what must survive” using a few musical comparisons; it is not a claim that one taste vector describes the person. Success unlocks controlled phrase-scale transformations and C23 foreshadowing. Failure returns the product to explicit authored anchors, which remain useful.

Explore symbolic/audio hybrid patch-level resynthesis only as a later optional asset tool, with licensed training/weights and captured output provenance. Never tie transport, project loading or baseline beat creation to it. Continue waveform-generation research only if it supplies editable/controllable value beyond sample/procedural methods under an affordable device/cost envelope. Kill criteria: repeated constraint failures, weak human preference, high per-session cost or loss of authorship.

## 14. Three things to build, three not to build, one bet

**Build:** a shared scoped proposal/evidence contract; the Pocket Negotiator; fast, inspectable, identity-preserving audition families.

**Do not build now:** a proprietary general audio foundation model; an autonomous always-on project editor; a new all-encompassing DAW object model and giant chat interface.

**The single most important bet:** producers will choose a workstation that helps them explore _musical relationships while keeping their identity intact_, provided each intervention is immediately audible, editable and reversible. Test that claim before funding a grand AI platform. The boldest research extension is C24, not a prerequisite for the core bet.

## 15. Open questions that materially change strategy

1. Which three producer segments actually use KYX repeatedly, and what are their genres, devices and session sizes? Without this, desirability scores remain assumptions.
2. Is the intended “our AI” the existing local ONNX/intent system, a particular reasoning provider, or an internal hosted service? The contract strategy is portable; latency, privacy and operating cost differ materially.
3. What do real cold and warm four-bar renders cost with representative instruments, returns and modulation? If preview is too slow, prioritize cached event transforms and one alternative before richer models.
4. Are scheduled events and live/offline results stable for all supported voices, automation and stochastic devices? Architecture alone cannot answer this.
5. How should a selected occurrence of a shared pattern behave? This choice changes proposal scope, undo and user trust.
6. Which existing context consumers use musical evidence today, and which still see effect-only or brief-only summaries? Presence of the snapshot tool does not establish universal grounding.
7. Can locks cover perceived attack as well as note-on? If not, groove identity should initially protect events and expose audio caveats explicitly.
8. What rights-cleared samples and opt-in producer projects can support listening studies? No dataset acquisition or rights permission is assumed by this document.
9. Do producers prefer suggestions while making a beat, or only when they explicitly get stuck? This determines notification policy and whether proactive tools should exist.
10. How much explicit feedback will users give before it disrupts flow? If the answer is almost none, authored constraints should outperform a personalization roadmap.
11. Which heavy model artifacts are actually available in deployed builds, and which are developer-only? Hash manifests, flags and code paths are insufficient deployment proof.
12. What is the team's net maintenance capacity after DAW reliability work? Understaffing should shrink the portfolio to one loop, not turn safety/verification into an aspiration.

## 16. External research and competitive source notes

Sources were accessed during this research on 28 October 2026. These primary sources support narrow claims; none establishes KYX's runtime performance or worldwide feature uniqueness.

- **S01 — Ableton:** selected-note transformations, scale-aware generation, apply/undo behavior and editable MIDI tools are documented in the [Live 12 MIDI Tools manual](https://www.ableton.com/en/live-manual/12/midi-tools/). Implication: generation and transformation alone are established competitors, not a new category.
- **S02 — Bitwig:** Operators and Expand can turn cycles into editable note/audio events; seeded versus random behavior matters. See [Operator-related functions](https://www.bitwig.com/userguide/latest/operator_functions/). Implication: repeatability and editable variation are competitive baselines; KYX must demonstrate contextual identity control.
- **S03 — Steinberg:** Cubase 15 documents melodic pattern generation and [Chord Assistant](https://www.steinberg.help/r/cubase-pro/15.0/en/cubase_nuendo/topics/chord_pads/chord_pads_chord_assistant_c.html); see [Cubase 15 new features](https://www.steinberg.net/cubase/new-features/). Implication: harmony assistance and pattern tools are not intrinsically novel.
- **S04 — W3C:** the [Web Audio 1.1 working draft](https://www.w3.org/TR/webaudio/) describes render quanta, defaulting to 128 frames, with a configurable hint in this draft. It is a standards document, not evidence of implementation uniformity or KYX timing precision.
- **S05 — ONNX Runtime:** [environment flags and session options](https://onnxruntime.ai/docs/tutorials/web/env-flags-and-session-options.html) document single-thread configuration, isolation requirements for WASM threading and runtime/binary compatibility. Implication: worker/thread setup is an engineering budget, not automatic free speed.
- **S06 — ONNX Runtime:** [Using WebGPU](https://onnxruntime.ai/docs/tutorials/web/ep-webgpu.html) documents the GPU provider and integration. Implication: select an execution path through capability/operator testing; do not infer arbitrary checkpoint portability.
- **S07 — ONNX Runtime:** [Deploying ONNX Runtime Web](https://onnxruntime.ai/docs/tutorials/web/deploy.html) supplies packaging guidance. Implication: weights, runtime assets and delivery/caching deserve separate review.
- **S08 — Copet et al.:** [Simple and Controllable Music Generation](https://arxiv.org/abs/2306.05284) demonstrates text/melody-conditioned audio-token generation with automatic and human evaluation. Implication: generated audio is a credible research branch; this paper does not establish event-level editable beat projects, phone feasibility or the right core for KYX.
- **S09 — Elizalde et al.:** [CLAP: Learning Audio Concepts From Natural Language Supervision](https://arxiv.org/abs/2206.04769) demonstrates joint language/audio representation learning. Implication: cross-modal retrieval is plausible; embedding similarity is not proof a kick fits an arrangement or that a sound is musically better.

The external review is intentionally selective rather than a comprehensive 2026 market/model survey. Verify current checkpoints, licenses, browser builds and hands-on competitor behavior before procurement or superiority claims. Future work should investigate task-specific beat/downbeat models and controllable symbolic models against the defined protocols, rather than select a new model merely because it is newer.
